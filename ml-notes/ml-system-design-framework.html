ML System Design Framework

The repeatable spine for any ML system design prompt. The strongest answers spend the first third scoping and never jump straight to a model. Drive this structure yourself — don't wait to be asked.

#The 6 steps

#1. Clarify & frame (~5 min)

Turn the vague prompt into a concrete ML problem. Pin down:

  • Business goal and who the user is
  • Scale — DAU, # items, QPS
  • Latency budget (e.g. ~100ms for ranking)
  • Freshness requirements
  • What "good" actually means

Open with: "First I'll align on the goal and success metric, then scale and latency, then ask what data we have."

#2. ML task & metrics

  • What does the model predict? Framing: ranking vs classification vs retrieval.
  • Offline metrics (AUC, NDCG, recall@k) AND online metrics (CTR, watch time, revenue) AND guardrails.
  • The key move: the proxy you optimize ≠ the thing you actually care about. Tune proxy weights against an online north-star (e.g. D7/D30 retention) via A/B tests.

#3. Data & features

  • Sources, labels (explicit vs implicit), leakage, cold start.
  • Feature families: user · item · user×item cross · context. The cross features are where ranking earns its keep.
  • Implicit-feedback bias — name all three:
    1. Exposure / selection bias (feedback loop — you only see labels for what you showed)
    2. Position bias (rank drives clicks regardless of quality)
    3. Noisy negatives (a skip ≠ a confirmed dislike)
    • Fixes: negative sampling, inverse propensity weighting / position-as-feature (zeroed at serving), exploration traffic to break the loop.

#4. Model

  • Start with a baseline, then justify complexity.
  • For large scale: multistage — retrieval → ranking → re-ranking.
  • Discuss tradeoffs, not just the fanciest option.

#5. Serving & scale

  • Retrieval: two-tower model + ANN index (HNSW / ScaNN / FAISS). Item embeddings precomputed offline & indexed; user tower runs once per request → single ANN lookup. The decoupling is the serving win.
  • Multiple retrieval sources unioned (personalized + trending + social + fresh-exploration).
  • Feature store, online vs batch inference, caching.

#6. Evaluation & iteration

  • Offline: ranking metric (NDCG), check calibration if probs feed downstream.
  • Online: A/B test vs north-star (retention) + guardrail metrics (reports, diversity, creator health).
  • Post-launch: monitor feature & prediction drift, watch online metrics decay, retrain regularly (daily/continuous for fast domains). Continuous retraining on biased logs amplifies bias → exploration matters long-term.

#Two-stage architecture cheat

Stage Catalog → out Job Model
Retrieval billions → thousands recall, cheap two-tower + ANN
Ranking thousands → hundreds precision heavy multi-task (MMoE)
Re-rank hundreds → ~10 diversity, policy rules + light model

#Cold start

  • Item: content embeddings at upload → retrievable immediately (also = freshness story).
  • User: onboarding preferences + popular/trending prior, let real interactions take over.

#Common ways people fail

  1. Jump straight to the model.
  2. Never define metrics properly (or don't connect offline ↔ online).
  3. Ignore data/serving reality.
  4. Circle instead of committing — state the structured answer up front.
  5. Use generic language instead of canonical component names.

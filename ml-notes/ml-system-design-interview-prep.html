ML System Design Interview Prep

#Stage 1: Business Objective

Goal: Understand WHY this system exists before touching anything technical. Interviewers want to see you think before building.

Questions to ask:

  • What is the core business goal? (revenue, safety, engagement, retention?)
  • What is the scale? (DAU, QPS, catalog size)
  • What latency is acceptable? (<100ms real-time, <1s near-real-time, batch OK?)
  • What data freshness is needed? (model needs to reflect events from 5 min ago or 5 days ago?)
  • Are there hard constraints? (regulatory, fairness, GDPR, COPPA, geographic)
  • Which is worse: false positives or false negatives?
  • Is there an existing system? What's broken about it?

Business metrics to know:

  • CTR, CVR (conversion rate), GMV
  • DAU/MAU, retention, session length
  • Map FP/FN cost to business: fraud FN = money lost, fraud FP = user friction

#Stage 2: ML Objective

Goal: Translate business goal → concrete ML problem.

Task types:

  • Binary classification — spam, fraud, click prediction
  • Multi-class — intent detection, category tagging
  • Ranking / LTR — search, feed, recommendations
  • Regression — price, ETA, bid value
  • Multi-task — predict CTR + CVR jointly
  • Generative — query rewriting, summarization

Business metric → ML proxy:

Business Metric ML Proxy
CTR AUC-ROC, log loss
Revenue CVR, predicted value
Relevance NDCG, MRR, MAP
Safety Recall @ high precision
Engagement Predicted watch time

Loss functions:

Problem Loss
Binary classification Binary cross-entropy (log loss)
Multi-class Categorical cross-entropy
Imbalanced classification Focal loss
Regression MSE / MAE / Huber
Ranking (pairwise) BPR loss, hinge loss
Ranking (listwise) LambdaRank, ApproxNDCG
Embeddings / contrastive Triplet loss, NT-Xent (SimCLR)
Distillation KL divergence + task loss

Key framing decisions:

  • Point-wise vs. pairwise vs. listwise ranking
  • Single-task vs. multi-task (shared bottom, mixture of experts)
  • Do you need calibrated probabilities or just a good ranking?

#Stage 3: High-Level Design

Goal: Sketch the end-to-end pipeline. Get the boxes and arrows right before going deep.

Standard pipeline:

Data sources → Feature engineering → Feature store
                                           ↓
                             Training pipeline → Model registry
                                           ↓
                             Serving layer → Prediction store / cache
                                           ↓
                             Logging → Feedback loop

Common architecture patterns:

Two-tower (retrieval)

  • User tower + Item tower → dot product → ANN index
  • Item embeddings precomputed offline
  • Used by: YouTube, Pinterest, TikTok for candidate generation

Cascade / Funnel (retrieval → ranking → re-ranking)

  • Retrieval (ANN, BM25, CF) → Ranking (GBDT, DNN) → Re-ranking (business rules, diversity)
  • Used in: search, feed ranking, ads

Sequence model (temporal)

  • LSTM / Transformer over user history → next-item prediction
  • Used in: Netflix, Spotify, TikTok

Real-time + batch hybrid

  • Batch features (stable, cheap) + real-time features (fresh, expensive) merged at serving

#Stage 4: Data & Feature Engineering

Goal: Where does data come from, how do you label it, what features do you extract.

Data sources:

  • User interaction logs (clicks, watches, purchases, skips, dwell time)
  • Item/entity metadata (title, category, price, content embeddings)
  • Context (time of day, device, location, session position)
  • Social graph (follows, co-views, shares)
  • External signals (weather, trending topics)

Labeling strategies:

  • Explicit: ratings, thumbs up/down — sparse, high quality
  • Implicit: clicks, watches, purchases — dense, noisy (click ≠ satisfaction)
  • Proxy labels: "watched >50% of video" as engagement positive
  • Human annotation: content quality, safety, NLP tasks

Label leakage gotchas:

  • Features computed after the event (e.g., final view count when predicting CTR)
  • Future data leaking into training window

Feature types:

  • User: demographics, long-term interests, embedding of ID
  • Item: category, price, recency, popularity, content embedding
  • User-item cross: past CTR on this category, historical spend
  • Context: time, device, session position, query

Feature engineering techniques:

  • Normalization / standardization — for neural nets
  • Log transform — heavy-tailed distributions (price, counts)
  • Bucketization — continuous → categorical
  • Target encoding — replace category with mean label (watch for leakage)
  • Embeddings — for high-cardinality IDs (users, items, queries)
  • Hashing trick — very high cardinality, reduces memory
  • Feature crosses — jointly encode two features (A × B)
  • Sequence aggregation — mean/sum/attention pooling over user history

Feature store:

  • Offline store: Hive, BigQuery, Spark — batch features, used in training
  • Online store: Redis, DynamoDB (managed by Feast / Tecton) — low-latency features at serve time
  • Point-in-time correctness: training features must reflect what was known AT prediction time

Class imbalance:

  • Downsample negatives (very common in click prediction — 1:100 or worse)
  • Calibration correction after downsampling negatives at keep-rate www: p=ps/(ps+(1−ps)/w)p = p_s / (p_s + (1-p_s)/w)p=ps​/(ps​+(1−ps​)/w), equivalent to adding log⁡w\log wlogw to the logit (a negative shift, since w<1w < 1w<1)
  • Weighted loss
  • Focal loss

#Stage 5: Model

Goal: Choose and justify your model. Know the tradeoffs.

Model cheat sheet:

Need Model
Fast baseline Logistic regression
Tabular data, ranking LightGBM / XGBoost
Large-scale retrieval Two-tower + FAISS ANN
Dense ranking DNN / DCN (Deep & Cross Network)
Sequential / session Transformer (SASRec, BERT4Rec)
Social graph GNN (GraphSAGE, PinSage)
Multimodal (text + image) CLIP-style dual encoder

Model tradeoffs:

Logistic Regression

  • Pros: fast, interpretable, calibrated, easy to debug
  • Cons: low capacity, needs manual feature engineering
  • When: baseline, very high QPS, features already good

GBDT (XGBoost, LightGBM)

  • Pros: handles tabular data extremely well, no normalization needed, built-in feature importance
  • Cons: doesn't handle embeddings, hard to do online learning
  • When: ranking, fraud, structured tabular data

DNN / MLP

  • Pros: learns feature interactions, handles embeddings end-to-end
  • Cons: more data needed, harder to debug, slower than GBDT
  • When: ranking with many features, multi-task setups

Two-Tower

  • Pros: item tower precomputed offline → fast retrieval
  • Cons: no user-item interaction at inference time (shallow)
  • When: retrieval at massive scale

Transformer

  • Pros: captures sequential context, state of the art for NLP
  • Cons: expensive to train and serve, needs lots of data
  • When: session modeling, NLP tasks, query understanding

GNN

  • Pros: captures social / graph structure natively
  • Cons: complex to build and serve
  • When: social feed ranking, fraud on transaction graphs

Training considerations:

  • Learning rate schedule: warmup + cosine decay
  • Regularization: L1/L2, dropout, early stopping
  • Positional bias: items shown first get more clicks — debias during training
  • Exposure bias: model only sees items that were previously shown

#Stage 6: Inference & Serving

Goal: Get predictions to users at scale, efficiently.

Batch vs. Real-time vs. Near-real-time:

Mode Latency Freshness Use case
Batch 0ms (precomputed) Stale (hours/days) Email recs, item embeddings
Near-real-time Seconds/minutes Fresh Trending, fraud streaming
Real-time <100ms Very fresh Feed ranking, search

Serving architectures:

  • Precomputed / lookup: store embeddings or scores in Redis, retrieve at serve time
  • Online inference: feature retrieval → model scoring → post-processing in budget
  • Cascade / multi-stage: cheap model for retrieval → expensive model on small candidate set

Latency optimization:

  • Quantization: FP32 → FP16 or INT8 (2-4x speedup, small accuracy loss)
  • Distillation: train small student from large teacher
  • Pruning: remove low-importance weights
  • Caching: cache predictions for popular user/item pairs
  • ANN for retrieval: FAISS, ScaNN, HNSW (millisecond-scale over billions of vectors)
  • Batching: group requests on GPU to maximize throughput

Scalability:

  • Horizontal scaling: replica-based, load balanced
  • GPU serving: large batches / transformers
  • CPU serving: low-latency tabular / small models
  • Feature lookup budget: Redis P99 ~1ms, DB can be 10-100ms — budget carefully

Deployment strategies:

  • Shadow mode: run new model in parallel, no user impact, compare offline
  • Canary: 1-5% traffic, monitor metrics
  • A/B test: randomized experiment, measure business metric
  • Interleaving: blend two ranked lists, measure clicks — faster signal than A/B
  • Multi-armed bandit: explore/exploit, useful when A/B is too slow

#Stage 7: Deep Dives & Improvements

Goal: Show depth by proactively naming hard problems and how you'd solve them.

Cold Start

  • New user: popular items, context features (device, referral), demographic priors
  • New item: content embeddings (image, text, metadata), zero-shot via pretrained model
  • Exploration: epsilon-greedy, Thompson sampling, UCB

Data Freshness / Training Latency

  • How fast does the model react to new events?
  • Options: real-time feature updates, online learning (SGD on stream), continuous training
  • Tradeoff: freshness vs. stability

Model Monitoring & Drift

  • Data drift: input distributions shift (COVID changed all user behavior overnight)
  • Concept drift: feature-label relationship changes
  • Detection: KL divergence, PSI (Population Stability Index), shadow scoring
  • Response: automated retraining triggers, alerting

Bias & Fairness

  • Selection bias: model trained on biased exposure (only seen items)
  • Popularity bias: popular items get over-recommended, feedback loop amplifies
  • Demographic fairness: disparate impact across groups
  • Debiasing: inverse propensity scoring (IPS), adversarial debiasing, constrained optimization

Feedback Loops / Echo Chambers

  • Model recommends what it predicts users like → users only see those items → model gets reinforced
  • Mitigations: exploration budgets, diversity constraints, counterfactual evaluation

Multi-Objective Optimization

  • Competing objectives: engagement vs. revenue vs. safety vs. diversity
  • Approaches: weighted sum of losses, Pareto optimization, constrained (maximize revenue s.t. engagement ≥ threshold), mixture of experts per objective

Reranking

  • After ranking: diversity (no 3 consecutive same artist), freshness boost, sponsored insertion, safety filtering

Privacy

  • Differential privacy: calibrated noise on gradients or outputs
  • Federated learning: train on-device, aggregate updates
  • ID hashing = pseudonymization only; not a formal privacy guarantee

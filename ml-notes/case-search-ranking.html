Case Study: Search Ranking

Search is recommendation with an explicit query: the user tells the system what they want, so relevance is sharper, the latency budget is tighter, and the labels are more biased than almost anywhere else.

This case study works one reference design end to end: a site search box over a large catalog of documents (products, articles, listings). The skeleton is the retrieve-then-rank funnel from Recommender Systems and the spine is the ML System Design Framework; this note adds what is specific to queries: understanding the query, mixing lexical and dense retrieval, learning to rank from clicks that are biased by position, and measuring quality when "relevant" is a judgment call.

What you'll be able to say after this chapter
  • Scope a search ranking problem and state a defensible latency and capacity budget with arithmetic.
  • Draw a four-stage pipeline (query understanding, hybrid retrieval, L1 and L2 ranking, re-ranking) and say what each stage optimizes.
  • Explain why BM25 and dense retrieval are complementary and how their candidates are fused.
  • Choose between pointwise, pairwise, and listwise learning to rank, and say why LambdaMART is a strong default.
  • Describe position bias and how to correct it (position features, inverse propensity weighting, interleaving, randomization) and what counterfactual LTR does at a glance.
  • Choose offline metrics (NDCG, MRR) and online metrics (CTR, abandonment, reformulation rate) and say how they can disagree.

#Problem statement and clarifying questions

Prompt. Design the ranking system behind a search box for a catalog of roughly 200 million documents. Users type short free-text queries; the system returns a ranked page of about 10 results.

Questions worth asking before drawing anything, and the assumption taken here for each:

Question Why it matters Assumption used
What is a "good" result? Decides label source and metric Satisfied session: clicked a result and did not reformulate quickly
Is intent navigational, informational, or transactional? Changes how much personalization helps Mixed; head queries mostly navigational or transactional
Scale: users, queries per user, catalog size Capacity and index design 50M daily users, 8 queries each, 200M documents
Latency budget Bounds model size and candidate counts 200 ms end to end at p99, 150 ms for the ranking path
Freshness Index update path New or changed documents searchable within minutes
Personalization allowed? Features and privacy Light personalization (locale, past engagement), no cross-user leakage
Languages and typos Query understanding scope Several languages; typos common on mobile
Human rating budget Label strategy A small rater pool for a few thousand judged queries per month

The task is a learning-to-rank problem layered on retrieval: given a query, pick a candidate set that contains the relevant documents, then order it so the most useful appear first. The ranking quality is measured on the top handful of positions, because users rarely look past the first screen.

#Requirements and back-of-envelope scale

Functional requirements: return a ranked list, support filters and facets, handle typos and synonyms, expose a debug explanation for each result for internal tools.

Non-functional requirements: p99 under 200 ms, availability that degrades gracefully (lexical-only results if the neural stages fail), and an index update path that does not require a full rebuild.

Traffic. Daily queries are 50×106×8=4×10850\times10^6 \times 8 = 4\times10^850×106×8=4×108. Average load is 4×108/86,400≈4,6304\times10^8 / 86{,}400 \approx 4{,}6304×108/86,400≈4,630 QPS. With a peak factor of about 3 for daily and regional shape, plan for roughly 13,90013{,}90013,900 QPS.

Compute per query. Suppose the retrieval union returns 1,000 candidates, a light first-pass ranker (L1) costs 0.01 ms per candidate on one core, and a heavier second-pass ranker (L2) scores the top 200 at 0.05 ms per candidate:

CPU per query=1000×0.01+200×0.05=20 ms\text{CPU per query} = 1000 \times 0.01 + 200 \times 0.05 = 20\ \text{ms}CPU per query=1000×0.01+200×0.05=20 ms

At peak the ranking CPU is 13,900×0.020≈27813{,}900 \times 0.020 \approx 27813,900×0.020≈278 cores, before headroom, feature fetch, and retrieval. Planning for two to three times that is reasonable, and a neural cross-encoder on a small final slice, if used, is better served from accelerators. Scoring all 200M documents with even the light model would cost 2×108×0.01 ms=2,0002\times10^{8}\times 0.01\ \text{ms} = 2{,}0002×108×0.01 ms=2,000 core-seconds per query, which is the whole reason the funnel exists.

Typical latency allocation inside the 150 ms ranking path: query understanding 10 ms, retrieval 30 ms (lexical and dense in parallel), fusion and feature fetch 20 ms, L1 10 ms, L2 30 ms, re-rank and snippet generation 20 ms, leaving slack for network and tail variance.

#Query understanding

Retrieval can only return what the query representation allows, so the cheap stages in front matter.

  • Normalization: lowercasing, Unicode normalization, tokenization appropriate to the language, stemming or lemmatization for the lexical side.
  • Spelling correction: a noisy-channel or sequence model that proposes corrections, with a conservative threshold; auto-correct only when confidence is high, otherwise show "did you mean".
  • Intent classification: a small classifier predicts intent (navigational, transactional, informational) and category. Its output is both a feature and a router (for example, restricting retrieval to a vertical).
  • Entity and attribute extraction: parse "red running shoes size 9" into structured filters plus free text.
  • Expansion and rewriting: synonyms and learned rewrites from session logs (query A frequently reformulated to B and then clicked). Rewrites trade recall for precision, so they are usually applied as soft additions with lower weight, not as replacements.

Query-level signals worth caching: the rewritten query, intent distribution, and top results for head queries. A small fraction of distinct queries accounts for a large share of traffic, so a result cache keyed by normalized query and locale absorbs a meaningful fraction of load; the cache TTL is a freshness decision.

Interview angle

Weak answers start with "train a ranking model". Strong answers first note that recall is capped by retrieval and query understanding, and that the ranker cannot recover a document that never entered the candidate set.

#Retrieval: lexical, dense, and hybrid

Lexical retrieval (BM25). An inverted index maps terms to postings lists; BM25 scores a document by term frequency saturation and inverse document frequency with length normalization:

BM25(q,d)=∑t∈qIDF(t) f(t,d) (k1+1)f(t,d)+k1(1−b+b ∣d∣avgdl)\text{BM25}(q,d) = \sum_{t\in q} \text{IDF}(t)\,\frac{f(t,d)\,(k_1+1)}{f(t,d) + k_1\left(1-b+b\,\frac{|d|}{\text{avgdl}}\right)}BM25(q,d)=t∈q∑​IDF(t)f(t,d)+k1​(1−b+bavgdl∣d∣​)f(t,d)(k1​+1)​

Here f(t,d)f(t,d)f(t,d) is the term count in ddd, ∣d∣|d|∣d∣ the document length, avgdl\text{avgdl}avgdl the corpus average, k1k_1k1​ controls saturation and bbb controls length normalization. It is fast, interpretable, handles rare exact tokens (part numbers, names) well, and needs no training. It fails on vocabulary mismatch: "cheap laptop" will not match "budget notebook".

Dense retrieval. A two-tower encoder maps the query and each document into a shared vector space; relevance is an inner product, and an ANN index returns nearest neighbors. This bridges vocabulary gaps and handles paraphrase, but it can blur exact matches and rare identifiers, and it requires training data and an embedding refresh path. The training recipe (in-batch negatives, hard negatives mined from non-relevant lexical top results, corrections for sampling bias) is covered in Two-Tower Retrieval.

Hybrid. The two retrievers fail differently, so combine them. Two common fusion options:

  • Reciprocal rank fusion (RRF): score each document by ∑r1/(k+rankr(d))\sum_{r} 1/(k + \text{rank}_r(d))∑r​1/(k+rankr​(d)) over retrievers rrr, with kkk around 60. It needs no score calibration across retrievers, which is why it is a good first choice.
  • Learned fusion: pass both scores and ranks as features into L1 and let the ranker decide. This usually wins once enough labeled data exists but requires the features to be present for documents retrieved by only one source (use a missing-value indicator, not zero).

Retrieval aims at recall at a candidate budget: the fraction of judged-relevant documents that appear in the top 1,000 union. Optimize that, and track it per query segment, because head and tail queries behave very differently.

Memory hook

BM25 is a precise but literal reader; dense retrieval is a loose but forgiving one. Hybrid uses both because their misses do not overlap.

#Ranking stages

L1 (cheap, wide). Takes about 1,000 candidates and keeps 200. It uses features available without expensive joins: retrieval scores, document static quality, query-document text match features (BM25 per field), freshness, popularity, and basic user locale. A gradient boosted tree (Gradient Boosting) is a strong fit: fast inference, robust to feature scale, handles missing values.

L2 (expensive, narrow). Takes the top 200 and orders the top 50. Richer features: personalization, historical click and conversion rates for the (query, document) pair or (query cluster, document), embedding similarity from a cross-attention model, and document quality models. Options:

Model Strength Cost or risk
LambdaMART (boosted trees with lambda gradients) Directly optimizes a rank-aware objective, strong with tabular features Limited use of raw text unless embeddings are features
Deep ranker over features (DCN style) Learns crosses, multi-task heads More data and serving cost
Cross-encoder (query and document jointly in a transformer) Best text relevance Latency; confined to the top 20 to 50
LLM-based reranker Strong on complex queries Highest latency and cost; use on a small slice or offline to produce labels

A pragmatic design uses LambdaMART as L2 with a cross-encoder score as one input feature computed on the top slice only.

Re-rank. Rules and light models apply diversity (avoid ten near-duplicates), freshness boosts for time-sensitive intents, business constraints (availability, region, safety filters), and de-duplication. Keep this layer thin and auditable.

#Learning to rank

Three formulations, in order of how much they use the list structure:

  1. Pointwise: predict a relevance grade or click probability per document with regression or classification. Simple, but optimizes a loss that is not rank-aware.
  2. Pairwise: for documents i,ji, ji,j with yi>yjy_i > y_jyi​>yj​ for the same query, minimize a loss on the score difference, for example the RankNet form
    Lij=log⁡(1+e−σ(si−sj))\mathcal{L}_{ij} = \log\bigl(1 + e^{-\sigma (s_i - s_j)}\bigr)Lij​=log(1+e−σ(si​−sj​))
    where sis_isi​ is the model score and σ\sigmaσ a scale.
  3. Listwise: optimize a list-level objective directly or through a smooth surrogate (ListNet softmax cross-entropy over the list, or LambdaRank).

LambdaRank and LambdaMART. Instead of differentiating a non-smooth metric, LambdaRank defines the gradient for each pair as the pairwise gradient scaled by how much swapping the pair would change the metric:

λij=−σ1+eσ(si−sj)  ∣ΔNDCGij∣\lambda_{ij} = \frac{-\sigma}{1 + e^{\sigma(s_i - s_j)}}\;\bigl|\Delta \text{NDCG}_{ij}\bigr|λij​=1+eσ(si​−sj​)−σ​​ΔNDCGij​​

Pairs that matter for the top of the list get larger gradients. LambdaMART plugs these lambdas into gradient boosted trees. It remains a strong default because tabular features dominate in many ranking stacks, the training is stable, and inference is fast.

Click bias and position bias. Raw clicks are not relevance. A document at position 1 is clicked more because it is seen more, regardless of quality. Treat the click probability as the product of examination and relevance:

P(click∣d,k)=P(examine∣k)⋅P(relevant∣d)P(\text{click} \mid d, k) = P(\text{examine} \mid k)\cdot P(\text{relevant} \mid d)P(click∣d,k)=P(examine∣k)⋅P(relevant∣d)

where kkk is the displayed position. If examination probability depends only on position, then training on raw clicks learns the old ranker's ordering back. Remedies:

  • Position as a feature, zeroed or fixed at serving. Simple and common; works if the model can separate position effects from content effects. The risk is that the model leans on the position feature and under-fits content.
  • Inverse propensity weighting (IPW). Weight each clicked example by 1/P(examine∣k)1/P(\text{examine}\mid k)1/P(examine∣k). Propensities are estimated from randomization experiments (swap positions on a small share of traffic) or from EM-style estimation using result pairs shown at different positions. High weights inflate variance, so clip them.
  • Randomization and exploration. A tiny shuffle bucket (for example a fraction of a percent of traffic, within one adjacent swap) gives unbiased signals at a measurable cost.
  • Click models (cascade, dynamic Bayesian networks) that explain clicks as examination along the list.
  • Trust bias and context bias (clicks on a result depend on neighbors, and users trust top results) are second-order but appear when propensities are poorly estimated.

Counterfactual LTR at a glance. Counterfactual learning to rank treats logged clicks as outcomes of a logging policy and uses importance weighting to estimate how a new ranker would have performed, without deploying it. The estimator is unbiased only if the propensity model is right and every relevant document had nonzero exposure. In practice, it is used to select among candidate rankers offline before an A/B test and to weight training, with the clipping and variance caveats above. It does not replace online experiments; see A/B Testing & Experimentation.

Common mistake

Training the next ranker on clicks produced by the current ranker without any bias correction. Offline metrics against those same clicks will look excellent, because the new model reproduces the old ordering.

#Features

Group features by what produces them so each can be given the right freshness and the right store (ML in Production):

Family Examples Notes
Query Length, intent distribution, language, historical click entropy, query frequency Batch plus cached
Document Static quality, age, popularity, field lengths, authority, price or availability Batch, with streaming for availability
Query-document BM25 per field, embedding cosine, term coverage, proximity, historical (query cluster, document) CTR Mixed; computed at request time or from joins
User and context Locale, device, coarse engagement history, session so far Online store; privacy review
Retrieval Source (lexical, dense, both), source scores and ranks Free, and strong

Rules of thumb: prefer rate features with smoothing (for example Bayesian-smoothed CTR) over raw counts, bucket and clip heavy-tailed counts, keep a missing indicator for sparse features, and ensure the same transformation code runs in training and serving to avoid Training-Serving Skew. Historical click features computed over a window that includes the target impression are a classic source of Data Leakage: compute them as of the time before the query.

#Labels: clicks versus human ratings

Source Strength Weakness
Clicks, dwell, conversions Abundant, reflects real use, fresh Position and presentation bias, noisy, favors clickbait
Skips and reformulations Weak negative signal A skip may mean the snippet already answered the query
Human relevance ratings (graded 0 to 4) Cleaner, consistent, can cover tail queries Expensive, slow, rater disagreement, may not match user intent
LLM-produced judgments Cheap and scalable Needs calibration against humans; can share blind spots with the ranker

A practical blend: train the main ranker on debiased click-derived labels (weighted by purchase or long-click rather than raw click), and keep a golden set of human-judged queries stratified by head, torso, and tail, used for evaluation, for sanity-checking offline metrics, and as an auxiliary training signal. Measure inter-rater agreement; if raters disagree with each other, the ceiling on any metric is low and metric differences below that noise are not meaningful. LLM-based judges can extend coverage but should be audited on a human sample and not used as the sole gate.

Negatives: documents shown above a clicked document are more reliable negatives than those never shown; unshown documents are unlabeled, not negative. Hard negatives for dense retrieval training can be mined from lexical top results the user skipped.

#Metrics

Offline ranking quality. Definitions and derivations live in Ranking Metrics; the essentials here:

DCG@k=∑i=1k2reli−1log⁡2(i+1),NDCG@k=DCG@kIDCG@k\text{DCG@k} = \sum_{i=1}^{k}\frac{2^{rel_i}-1}{\log_2(i+1)},\qquad \text{NDCG@k}=\frac{\text{DCG@k}}{\text{IDCG@k}}DCG@k=i=1∑k​log2​(i+1)2reli​−1​,NDCG@k=IDCG@kDCG@k​

Worked check: a page with graded relevance [3,2,0,1][3,2,0,1][3,2,0,1] has DCG=7/1+3/1.585+0+1/2.322≈9.32\text{DCG}=7/1 + 3/1.585 + 0 + 1/2.322 \approx 9.32DCG=7/1+3/1.585+0+1/2.322≈9.32; the ideal order [3,2,1,0][3,2,1,0][3,2,1,0] gives ≈9.39\approx 9.39≈9.39, so NDCG@4 is about 0.9930.9930.993. Moving the grade-3 document to position 3 would cost far more than moving the grade-1 document, which is why NDCG weights the top.

MRR averages 1/rank1/\text{rank}1/rank of the first relevant result and suits navigational queries with one right answer. With first-relevant ranks 2, 1, and 4 across three queries, MRR=(0.5+1+0.25)/3≈0.583\text{MRR} = (0.5 + 1 + 0.25)/3 \approx 0.583MRR=(0.5+1+0.25)/3≈0.583.

Also track: recall at the candidate budget for retrieval, a per-segment breakdown (head, torso, tail, language, category), zero-result rate, and calibration if scores feed another system (Calibration).

Online. CTR on the first page, click position distribution, long-click or satisfaction rate, abandonment (no click and no reformulation soon after), reformulation rate, time to first click, and downstream conversion. CTR alone can be gamed by attractive but unhelpful results, and abandonment can rise even when the answer was in the snippet. Pre-register guardrails: latency, zero-result rate, share of traffic with errors, and diversity.

When offline and online disagree. Reasons include a biased offline label set, a ranker that changes the exposure distribution (so logged labels no longer cover its outputs), a gain on tail queries masked by head traffic, and novelty effects. Use interleaving (blend two rankers' lists and attribute clicks) for sensitive, low-traffic comparisons, then a full A/B test for ship decisions (A/B Testing & Experimentation).

Interview angle

Name both the offline metric and the reason it can mislead. "NDCG improved but abandonment rose" is a realistic scenario to discuss, with candidate causes and the next diagnostic cut by query segment.

#Latency budget and capacity

Stage Budget (p99) Levers
Query understanding 10 ms Cache by normalized query; small models
Retrieval (parallel lexical and dense) 30 ms Sharding, early termination, quantized ANN, tiered index
Fusion + feature fetch 20 ms Batched feature reads, co-located store, precomputed doc features
L1 10 ms Tree models, vectorized scoring
L2 30 ms Candidate cap, distillation, accelerator batching
Re-rank + snippets 20 ms Precomputed snippets for head docs
Slack 30 ms Hedged requests, timeouts with fallbacks

If a stage exceeds its deadline, serve the previous stage's order rather than failing: a degraded but valid ranking beats a timeout. Distillation of the heavy ranker into a lighter model, feature pruning by importance per millisecond, and caching of head-query pages all reduce cost; see the efficiency discussion in ML in Production.

#Freshness and indexing

Two paths: a batch path (full index and embedding refresh nightly or weekly) and a streaming path (new or updated documents indexed within minutes via an append-only delta index merged periodically). If 2 percent of the 200M documents change per day, that is about 4 million documents to re-embed and re-index daily, roughly 46 per second on average; small enough for a streaming path. Dense vectors for new documents come from the same encoder, so they are comparable to existing ones; when the encoder is retrained, re-embed everything and swap the index atomically, since mixing embedding versions in one index breaks distances.

Time-sensitive queries (news, events) need a freshness feature and, for the right intents, a boost in re-rank. The query intent classifier can flag "recency-sensitive" so the boost does not leak into evergreen queries.

#Cold start

  • New documents. No click history, so engagement features are missing. Use content-based features (text, embedding, source quality), smoothed priors from similar documents, and a small exploration allowance that shows new items at controlled positions to gather clicks. See Cold Start.
  • New queries (tail). Lexical plus dense retrieval and text-match features carry these; query-level behavior features are absent, so models need to degrade gracefully with missing values rather than imputing zero.
  • New users. Use locale, device, and query only; personalization features default to population priors.

#Training and deployment

Training data comes from impression logs joined with clicks within a session window, with position recorded. Split by time (and ideally by query group) so that near-duplicate impressions of the same query do not leak across train and test; see Model Evaluation & Validation. Retrain the rankers on a regular cadence, daily to weekly depending on how fast behavior shifts, and retrain the embedding model less often with a mandatory index rebuild.

Rollout: offline evaluation on the golden set and a replay of logged queries, shadow scoring to compare outputs and latency, a small canary, then an A/B test with interleaving for sensitivity. Keep the previous ranker and index version hot for instant rollback.

Monitoring: input feature distributions and prediction distribution (population stability against a reference window), retrieval recall proxies (fraction of clicks on documents retrieved by only one source), zero-result rate, latency per stage, and online metrics per query segment. See Data Drift vs Concept Drift for the distinction between a shift in inputs and a shift in what users want.

#Failure modes

Common mistake

Declaring success on an aggregate metric dominated by head queries. Tail queries are where most distinct intents live and where hybrid retrieval and text features help most.

  • Training on raw clicks from the incumbent ranker without bias correction reproduces its ordering; treat unshown documents as unlabeled.
  • RRF fuses ranked lists without score calibration.

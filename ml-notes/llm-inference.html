LLM Inference: Decoding, KV Cache & Serving

Training teaches the distribution; inference is how you sample from it under latency and dollar constraints.

Autoregressive transformers generate one token at a time. The forward pass you studied for training is only half the story: serving adds scheduling, memory accounting, and a policy for choosing each token. That simple loop hides a systems problem: decoding policy (greedy vs nucleus), KV cache memory, prefill vs decode bottlenecks, batching, quantization, and speculative tricks. This chapter is what ML engineers need after the architecture chapter — enough to reason about vLLM, cost per 1K tokens, and why your 70B model feels fast on short prompts but crawls on long threads.

What you'll be able to say after this chapter
  • Describe the autoregressive loop and how it differs from teacher forcing in training.
  • Pick greedy, beam, temperature, top-kkk, top-ppp for a scenario and name repetition penalties.
  • Write the KV cache memory formula and explain GQA/MQA savings.
  • Contrast prefill (compute-bound) vs decode (memory-bandwidth-bound) and TTFT vs ITL.
  • Explain continuous batching, PagedAttention, weight-only INT4, and speculative decoding at a high level.
  • Name the cost/latency trade-off and mention constrained decoding briefly.

#Autoregressive generation

Training maximizes ∑tlog⁡pθ(xt∣x<t)\sum_t \log p_\theta(x_t \mid x_{<t})∑t​logpθ​(xt​∣x<t​) with teacher forcing — the model always sees gold prefixes. Inference feeds back its own samples:

  1. Encode prompt tokens x1:Tx_{1:T}x1:T​ (may fill KV cache).
  2. Sample xT+1x_{T+1}xT+1​ from p(⋅∣x≤T)p(\cdot \mid x_{\le T})p(⋅∣x≤T​).
  3. Append; repeat until EOS or budget.

Each step is one forward pass producing logits z∈R∣V∣z \in \mathbb{R}^{|\mathcal{V}|}z∈R∣V∣; decoding turns zzz into a token id; the embedding of that id becomes the next input. The objective at train time is cross-entropy / MLE; at serve time it is latency × quality × cost.

Memory hook

Training looks ahead with correct homework; inference writes the exam one word at a time and can't erase.

Interview angle

"How does GPT generate?" Not "it predicts the next word" — autoregressive factorization of joint p(x)p(x)p(x), one conditional per step, with decoding policy and KV cache determining wall-clock.

Rapid fire — Autoregressive

Chain rule over tokens. One forward per new token at decode. Logits → decoding → append. Teacher forcing only in training. Vocab size sets final linear cost. Hooks: Tokenization, hallucination grows with loose sampling.

#Decoding strategies

Let ziz_izi​ be logits for token iii. Common transforms:

Strategy Rule When to use
Greedy xt=arg⁡max⁡izix_t = \arg\max_i z_ixt​=argmaxi​zi​ Low-latency drafts, code with grammar hints
Beam search Keep top BBB partial sequences MT, summarization (metric-friendly, dull chat)
Temperature Softmax on z/Tz/Tz/T; T<1T<1T<1 sharper Control randomness monotonically with TTT
Top-kkk Sample among kkk largest logits Fixed tail cap; still breaks on flat tails
Top-ppp (nucleus) Smallest set with cum. prob ≥p\ge p≥p Chat, creative writing — adaptive width
Repetition penalty Down-weight logits of tokens in recent context Reduce loops; can harm list-like facts

Sampling vs search: beams optimize approximate joint likelihood of a finished string; i.i.d. sampling at each step does not sample from the sequence joint unless you temper and penalize carefully. For chat products, top-ppp + temperature + repetition penalty is the usual stack; for benchmarks with references, greedy or beam.

Trap

Lower temperature always "more factual" — false. It anchors to the model's mode, which can still be wrong confidently (hallucination).

Interview angle

Strong answers pair a strategy with a product constraint: latency (greedy), diversity (nucleus), metric (beam), safety (constrained + low temperature on structured fields).

#Beam search (sketch)

At step ttt, beam search keeps the top BBB partial sequences by log-probability ∑s≤tlog⁡p(xs∣x<s)\sum_{s \le t} \log p(x_s \mid x_{<s})∑s≤t​logp(xs​∣x<s​). Each beam expands ∣V∣|\mathcal{V}|∣V∣ children; prune back to BBB. Complexity scales with BBB and vocab — rarely used in low-latency chat at large ∣V∣|\mathcal{V}|∣V∣. Length normalization 1tα∑log⁡p\frac{1}{t^\alpha}\sum \log ptα1​∑logp avoids bias toward shorter strings.

#Logits processing pipeline (production)

Typical order: (optional) repetition/frequency penalties on logits → divide by temperature → top-kkk mask → top-ppp mask → softmax sample or argmax. Penalties are heuristic; they are not in the training loss.

See Decoding Strategies card for the 30s version.

Rapid fire — Decoding

Greedy = fast, repetitive. Beam = quality/latency trade for structured outputs. Temperature scales entropy. Top-ppp adapts to peaked/flat distributions. Penalties fix loops not truth. Mismatch with training (exposure bias) is structural — mitigated by RLHF/DPO, not decoding alone.

#The KV cache

For layer ℓ\ellℓ, attention needs K(ℓ),V(ℓ)K^{(\ell)}, V^{(\ell)}K(ℓ),V(ℓ) for all past positions. Recomputing them each step is O(t2)O(t^2)O(t2) cumulative work over length ttt. Caching stores past K,VK,VK,V; each decode step only computes q,k,vq,k,vq,k,v for the new token and appends to cache.

Per layer, stored tensors (per batch element):

K,V∈RHkv×t×dheadK, V \in \mathbb{R}^{H_{\text{kv}} \times t \times d_{\text{head}}}K,V∈RHkv​×t×dhead​

Memory estimate (bytes):

KV mem≈2×L×Hkv×dhead×seq_len×batch×bytes\text{KV mem} \approx 2 \times L \times H_{\text{kv}} \times d_{\text{head}} \times \text{seq\_len} \times \text{batch} \times \text{bytes}KV mem≈2×L×Hkv​×dhead​×seq_len×batch×bytes
  • Factor 2 = store both KKK and VVV.
  • LLL = transformer layers; HkvH_{\text{kv}}Hkv​ = KV heads (HHH in MHA, 111 in MQA, ggg in GQA).
  • Often Hkv×dhead=dmodelH_{\text{kv}} \times d_{\text{head}} = d_{\text{model}}Hkv​×dhead​=dmodel​ (same total KV width as MHA).

Example sanity check: L=32L=32L=32, Hkv=8H_{\text{kv}}=8Hkv​=8, dhead=128d_{\text{head}}=128dhead​=128, seq = 4096, batch = 1, FP16 (2 bytes):
2×32×8×128×4096×1×2≈0.542 \times 32 \times 8 \times 128 \times 4096 \times 1 \times 2 \approx 0.542×32×8×128×4096×1×2≈0.54 GB per sequence. With full multi-head attention (Hkv=32H_{\text{kv}} = 32Hkv​=32, as in Llama-2-7B) the same context costs ≈2.1\approx 2.1≈2.1 GB — GQA's 4× saving, and the reason KV memory, not weights, caps batch size at long contexts.

Memory hook

2LKVT — 2 tensors, L layers, KV heads (not Q), T tokens, times width and batch.

Interview angle

When asked "why GQA?", don't say "faster attention" vaguely — decode is bandwidth-bound reading growing KV; sharing KV heads shrinks memory and bytes moved per token.

#Stepping through one decode iteration

For token at time ttt (1-indexed after prompt):

  1. Embed xtx_txt​ → run one transformer layer at a time.
  2. At layer ℓ\ellℓ: compute qt(ℓ)q_t^{(\ell)}qt(ℓ)​ from current hidden; kt(ℓ),vt(ℓ)k_t^{(\ell)}, v_t^{(\ell)}kt(ℓ)​,vt(ℓ)​ from current hidden; concatenate kt,vtk_t, v_tkt​,vt​ along sequence dim to cached K1:t−1,V1:t−1K_{1:t-1}, V_{1:t-1}K1:t−1​,V1:t−1​.
  3. Attention for position ttt uses queries at ttt only, but keys/values for 1..t1..t1..t — complexity O(t)O(t)O(t) per layer per step → O(t2)O(t^2)O(t2) summed over generation (hence cache).
  4. Final hidden → logits → decode → xt+1x_{t+1}xt+1​.

Without cache, you'd re-run layers 1..ℓ\ellℓ for all positions 1..t1..t1..t each step — O(t2L)O(t^2 L)O(t2L) forward redundancy.

Details: KV Cache card; architecture: Transformers & Attention (MQA/GQA).

Rapid fire — KV cache

Cache K,VK,VK,V only. Q recomputed each step. Memory linear in seq_len. Formula: 2LHkvdheadTB×2 L H_{\text{kv}} d_{\text{head}} T B \times2LHkv​dhead​TB× bytes. Quantized KV possible. Prefill fills cache once; decode appends.

#Prefill vs decode

Two phases in a request:

Phase What runs Typical bottleneck Latency metric
Prefill All prompt tokens in parallel (causal) Compute (matmul FLOPs on long prompt) Time to first token (TTFT)
Decode One new token per forward Memory bandwidth (read full KV each layer) Inter-token latency (ITL)

Long prompts: prefill dominates TTFT. Long generations: decode steps add up; each step touches the entire KV history — why context length hurts more at serve than a naive "linear in tokens" intuition suggests.

Throughput (tokens/s) rises with batching multiple requests — until KV memory fills the GPU.

Rapid fire — Prefill/decode

Prefill = parallel prompt; decode = serial tokens. TTFT vs ITL. Compute-bound prefill, bandwidth-bound decode. FlashAttention helps prefill/training IO; GQA helps decode KV. Continuous batching mixes prefill+decode across users.

#Hardware mapping (brief)

One decode forward is mostly matrix multiplies + reading KV. Large models use tensor parallelism (split weight columns across GPUs; all-reduce activations) or pipeline parallelism (layer stages). Data parallel duplicates weights for independent batches — distinct from sharding a single 70B.

The ML story ties to systems: if ITL is high, profile whether you are KV-bandwidth limited (long context, many users) or compute limited (huge vocab softmax, unquantized weights). PyTorch torch.compile and vendor kernels matter at the margin; KV and batching dominate SaaS economics.

Rapid fire — Parallelism

TP = split layers/weights across GPUs on one request. PP = stages. DP = replicate for throughput. EP for MoE experts. Pick based on model size vs batch size.

#Continuous batching and PagedAttention (vLLM)

Static batching waits for the slowest sequence — GPUs idle. Continuous batching (iteration-level scheduling) admits new requests and finishes others between decode steps without draining the whole batch.

PagedAttention (vLLM): treat KV cache like virtual memory pages — non-contiguous fixed-size blocks, allocated on demand. Cuts fragmentation when sequences differ in length; enables higher batch utilization.

Interview sound bite: KV is dynamic-length per request; paged blocks let the scheduler pack GPUs without reserving max-length rectangles for every slot.

Interview angle

"How would you serve 1000 concurrent chats?" — mention batching, max context, KV memory accounting, paged KV, separate prefill/decode queues, and autoscaling on TTFT SLOs.

Rapid fire — Serving

Continuous batching = dynamic req sets per step. PagedAttention = fragmented KV blocks. vLLM ecosystem standard for OSS serving. Tensor parallel for large models across GPUs. LoRA adapters add memory headroom constraints.

#Quantization

Type What is quantized Typical use
INT8 weight + activation Both Throughput on supported kernels; needs calibration
Weight-only INT4/INT8 WWW in linear layers GPTQ, AWQ — shrink memory, matmul in FP16/BF16 accumulate
FP8 Weights and/or activations H100-class hardware

GPTQ / AWQ — post-training weight quantization with error compensation; AWQ protects "salient" weights. Trade-off: bandwidth and capacity vs perplexity regression; 4-bit often fine for 70B serve, eval on your tasks.

Activation quantization is harder (dynamic ranges); weight-only is the default for LLM inference when people say "INT4 model."

AWQ vs GPTQ (interview): both are post-training 4-bit weight methods. GPTQ minimizes layer-wise squared error with approximate second-order info (Hessian). AWQ identifies salient weight channels (where activations are large) and protects them during quant — often better perplexity at same bit-width. Neither removes need for downstream eval on your tasks.

KV cache quantization (FP8/INT8 KV) is emerging: halves KV bytes with task-dependent quality impact — separate from weight quant.

Interview angle

"Why not train INT4 from scratch?" — PTQ on a strong FP16/BF16 checkpoint is cheaper; QAT exists but is heavier. Production path: train bf16 → GPTQ/AWQ → serve with kernels that dequant on the fly.

Rapid fire — Quantization

Weight-only = smaller, faster load, less KV untouched. GPTQ/AWQ = PTQ recipes. INT4 ≈ 4× weight compression. Watch outliers in layers. Distillation (separate) transfers behavior to smaller dense models.

#Speculative decoding and distillation

Exposure bias reminder: the model was trained on gold prefixes but tested on its own samples — errors compound. Decoding tricks (nucleus, penalties) mitigate symptoms; RLHF / on-policy fine-tuning (RLHF vs DPO) addresses the train–test mismatch in distribution.

Speculative decoding: a draft model (small, fast) proposes kkk tokens; the target large model validates them in parallel (one batched forward). Accept tokens while draft agrees with target distribution; on mismatch, resample — exact same distribution as target decoding under standard schemes, lower latency when draft is accurate.

Distillation: train a smaller student on teacher logits/outputs — not a runtime trick but a permanent cap-ex swap (training chapter). Different question from speculative decode at serve time.

Interview angle

Don't conflate speculative decoding (same model quality, draft speedup) with quantization (approximate weights) or distillation (different model).

Rapid fire — Speedups

Speculative = draft + verify. Medusa/EAGLE variants learn draft heads. Distillation = offline shrink. RAG adds prefill tokens — hits TTFT and KV, not just param count.

#Cost and latency trade-offs

Rough mental model for cost per 1K tokens:

cost∝GPU-hour pricethroughput (tokens/s)×utilization\text{cost} \propto \frac{\text{GPU-hour price}}{\text{throughput (tokens/s)} \times \text{utilization}}cost∝throughput (tokens/s)×utilizationGPU-hour price​

Levers:

Lever Latency Cost Quality risk
Smaller model / quant ↓ ↓ ↑
GQA / shorter context ↓ ITL ↓ memory small
Greedy vs nucleus ↓ samples same repetition vs diversity
Bigger batch ↑ TTFT tail ↓ $/token none if scheduled well
Speculative decode ↓ decode steps extra draft GPU low if draft good

SLO framing: interactive chat optimizes TTFT + ITL; offline batch optimizes $/token. Long input RAG pays prefill on retrieved + prompt tokens — budget context in product design.

Rapid fire — Economics

Decode steps × batch × model width = wall-clock. KV caps concurrent users. Quant and GQA buy seats on same GPU. Measure on your prompt length distribution, not marketing benchmarks.

#Batching math: tokens per second

If average output length is LoutL_{\text{out}}Lout​ and batch size is BBB, sustained decode throughput ≈B/ITL\approx B / \mathrm{ITL}≈B/ITL tokens/s (one token per sequence per step). Prefill adds a one-time cost proportional to prompt length LinL_{\text{in}}Lin​ per request. Total GPU-seconds per request scales roughly as:

T≈cprefillLin+cdecodeLoutT \approx c_{\text{prefill}} L_{\text{in}} + c_{\text{decode}} L_{\text{out}}T≈cprefill​Lin​+cdecode​Lout​

Constants absorb width, layers, and quant — exact profiling beats theory. Raising BBB improves cdecodec_{\text{decode}}cdecode​ amortization until KV fills memory.

Memory hook

Prefill once, decode many — long answers multiply ITL steps; long prompts hit TTFT once but inflate KV for the whole session.

#Adapters at inference (LoRA)

Low-rank adapters add ΔW=BA\Delta W = B AΔW=BA to frozen weights. Serving implication: either merge LoRA into base weights offline (one graph) or run dual matmuls per layer (base + adapter). Multi-tenant hosts may load hundreds of adapter sets — memory and routing become product problems, not just forward-pass math.

Rapid fire — LoRA serve

Merge for speed; separate for hot-swapping adapters. Base model quantized once; adapter precision choice affects quality.

#Structured output and constrained decoding

When outputs must follow JSON, grammar, or tool call schemas, constrained decoding masks illegal logits at each step (finite-state machine, grammar compiler, or bitmask on vocab). Libraries (Outlines, guidance, XGrammar) compile constraints once per request.

Brief: reduces post-hoc repair and hallucination-shaped formatting errors; adds CPU-side mask work; still needs a capable base model for semantics.

Memory hook

Constrained decoding = legal moves only on the logit chessboard each turn.

Rapid fire — Structured

Mask illegal tokens before softmax. JSON/tool APIs in production. Complements eval schema checks. Not a substitute for validation on side effects (tool execution).

#Multi-turn, chat templates, and context growth

Chat models wrap user/assistant turns in a template (<|user|>, [INST], etc.) defined at tokenization time. Each new user message re-prefills the full history (unless you cache prefix KV externally). Multi-turn sessions therefore:

  • Grow KV linearly with total tokens in context.
  • Re-run attention over all prior turns on every new user message at prefill — TTFT rises with thread length.
  • Need truncation or summarization policies in product (keep last NNN tokens, summarize middle).

Prefix caching (same system prompt across users): if many requests share an identical long system block, some engines cache KV for that prefix and reuse — amortizes RAG-style static instructions.

Interview angle

"Why did my chatbot slow down after 50 turns?" — context length and prefill on full history, not model "getting tired."

Rapid fire — Multi-turn

Templates define token pattern. KV stores full visible history. Truncate/slide window/product policy. Shared system prompt cache is a deployment optimization.

#Production monitoring (what to chart)

Offline perplexity does not predict serve health. Track TTFT p50/p99, ITL p50/p99, tokens/s/GPU, KV memory utilization, batch size, and preemption rate on queues. Quality: sample conversations + LLM eval / human review — latency SLOs and quality regressions decouple (quant can hurt one not the other).

Rapid fire — Monitoring

Separate latency SLOs from quality dashboards. Alert on OOM, queue depth, TTFT spikes. Log prompt/completion token counts per request for cost attribution.

#Common interview traps

Trap Fix
"KV cache saves FLOPs in training" Training uses full-sequence parallel attention; cache is inference
"Beam is always better" Wrong for open-ended chat; exposure to dull modes
"INT4 = 4× faster always" Speedup = memory bandwidth + kernel support; model-dependent
Confusing TTFT with total latency Long outputs: sum of ITLs dominates
Forget batch in KV formula Linear in batch — saturation is memory-limited
Interview angle

System design prompts ("serve Llama 70B to 10k users"): start with KV memory per user × concurrency, then decoding, then quant/parallelism. ML-only answers miss the bottleneck.

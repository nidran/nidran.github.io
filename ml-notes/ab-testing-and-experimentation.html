A/B Testing & Online Experimentation

Offline metrics tell you what might happen; online experiments tell you what did.

A model can ace cross-validation and still fail in production — users react to latency, UX changes, and social influence in ways no holdout set captures. Online experimentation randomizes real traffic between control and treatment, estimates causal lift on business metrics, and is the gold standard for launch decisions in search, ads, and product ML. This chapter covers test design, hypothesis testing, sample size, variance reduction, ratio metrics, the pitfalls that inflate false positives, ranking-specific interleaving, and when multi-armed bandits complement fixed A/B tests.

What you'll be able to say after this chapter
  • Explain why offline evaluation is necessary but not sufficient for shipping.
  • Design an A/B test: hypothesis, unit of randomization, primary, guardrail, and north-star metrics.
  • State what a p-value is (and is not), Type I/II errors, and power, and compute sample size for a two-arm test.
  • Choose among z-test, t-test, Mann–Whitney, and bootstrap; apply the delta method to ratio metrics.
  • Name pitfalls: peeking, multiple comparisons, sample ratio mismatch, interference, and Simpson's paradox.
  • Contrast interleaving and bandits with classic A/B for ranking and explore/exploit.

#Why offline metrics are not enough

Offline evaluation assumes a frozen dataset and a fixed scoring rule. Production breaks both assumptions: the data distribution drifts (data drift), user behavior is strategic (they adapt to the product), and the full system — latency, ranking blend, guardrails — changes the experience. A recommender with higher offline NDCG can lose online if it surfaces niche items users ignore, or if inference slows scroll speed.

Offline metrics remain essential: they cheaply screen bad ideas, tune hyperparameters, and catch leakage before you burn traffic. The senior pattern is two gates: offline sanity (ranking metrics, calibration — see Calibration, Ranking Metrics) then a powered online test on metrics users and the business actually care about. Neither gate alone is enough.

#What offline still does well

Use offline evaluation to reject broken rankers (NDCG collapse), compare feature sets under cross-validation, and validate calibration before a risky pricing model goes live. Use online tests to measure system-level effects: ranking policy + UI + latency + exploration. Training-serving skew (ML in production) shows up only online — features computed differently in the batch scorer than the live path look great offline and die in prod.

#A/A tests and variance baselines

Before trusting any B result, run an A/A test: two identical experiences, split randomly. You should see no significant lifts on the primary metric if instrumentation is honest. A/A estimates empirical variance of your metric under null — useful for sanity-checking precomputed sample sizes. Repeated A/A failures mean broken bucketing, cookie churn, or metric bugs — fix those before burning a real test.

Memory hook

Offline = "does the model learn the past?" Online = "does the product win the future?"

Interview angle

Weak: "we'll A/B test after training." Strong: name what offline cannot see (network effects, UX, latency, long-term retention) and which metric you'll randomize on, with guardrails for revenue and safety.

#Designing a test

#Hypothesis and randomization unit

Write a crisp null hypothesis H0H_0H0​: no difference between control and treatment on the primary metric. The alternative H1H_1H1​ is a directional or two-sided lift you care about (e.g. conversion increases by at least δ\deltaδ). Pre-register H0H_0H0​, the primary metric, α\alphaα, minimum detectable effect (MDE) δ\deltaδ, and planned duration before traffic arrives.

The unit of randomization must match how independence holds:

Unit Use when Pitfall if wrong
User Logged-in experience, one treatment per person Same user in both arms via cookies/devices
Session Anonymous traffic, short-lived experiments Same user gets inconsistent UX across visits
Request / page view Ultra-high volume, no stable user id Correlated requests from one user violate i.i.d.
Cluster (market, school) Interference between neighbors Underpowered if clusters are huge
Switchback (time blocks) Network effects, marketplace two-sided Seasonality and day-of-week confounds

Getting the unit wrong is not a detail — it invalidates standard errors and p-values.

#Primary, guardrail, and north-star metrics

  • Primary metric: the one whose lift decides ship/no-ship (conversion, revenue per user, dwell time). One primary; everything else is secondary.
  • Guardrail metrics: things that must not regress — crash rate, latency p99, spam reports, unsubscribe rate. A win on primary with a guardrail breach is a no-launch.
  • North-star / OEC (Overall Evaluation Criterion): long-horizon company health (retained revenue, LTV proxy). Often too noisy for a single test; use as context, not always as the test's only gate.

Align metrics with precision vs recall thinking: optimizing clicks (recall of engagement) may tank precision of satisfaction — guardrails encode that trade-off.

Rapid fire — Test design

Pre-register hypothesis, primary metric, α\alphaα, MDE, and nnn. Randomization unit = where independence lives. One primary metric; guardrails catch collateral damage. Offline screens; online proves causality. Wrong unit → wrong inference.

#Hypothesis testing refresher

Under H0H_0H0​ (no effect), the test statistic (difference in means, difference in proportions) has a known or estimable null distribution. The p-value is:

p=P(statistic at least as extreme as observed∣H0 true)p = P(\text{statistic at least as extreme as observed} \mid H_0 \text{ true})p=P(statistic at least as extreme as observed∣H0​ true)

It is not P(H0 true)P(H_0 \text{ true})P(H0​ true), not the false-positive rate, and not "probability the lift is real." A small ppp means: if there were truly no effect, data this extreme would be rare — evidence against H0H_0H0​, not proof.

Error Name Rate Meaning
Reject true H0H_0H0​ Type I α\alphaα (e.g. 0.05) False launch — noise looked like signal
Fail to reject false H0H_0H0​ Type II β\betaβ Missed a real win
Reject false H0H_0H0​ Power 1−β1-\beta1−β (often 0.8) Detect a real effect of size δ\deltaδ

Confidence intervals on the lift complement p-values: report "lift = 0.3% (95% CI: 0.1%–0.5%)" instead of only p=0.02p=0.02p=0.02. See also p-Values & Statistical Power and Math (§Statistics).

The golden misread

Never say "there's a 95% chance the variant is better." Say "under the null, this result would occur about 5% of the time" or give a CI for the effect size.

Interview angle

If asked "p = 0.03, what does that mean?" — conditional probability under H0H_0H0​, full stop. Bonus: mention you'd still check practical significance (δ\deltaδ vs CI), guardrails, and whether you peeked.

#Sample size and power

For a two-sample test with equal allocation and a difference in means (or proportions with σ2≈p(1−p)\sigma^2 \approx p(1-p)σ2≈p(1−p)), each arm needs approximately:

n≈2 (z1−α/2+z1−β)2 σ2δ2n \approx \frac{2\,\bigl(z_{1-\alpha/2} + z_{1-\beta}\bigr)^2\,\sigma^2}{\delta^2}n≈δ22(z1−α/2​+z1−β​)2σ2​

where δ\deltaδ is the MDE (absolute), σ2\sigma^2σ2 is per-unit variance under the null (or pooled estimate), α\alphaα is two-sided Type I rate, and power is 1−β1-\beta1−β.

Control conversion p0=0.10p_0 = 0.10p0​=0.10; you want to detect δ=0.01\delta = 0.01δ=0.01 absolute lift to 0.110.110.11 (relative +10%). Use σ2=p0(1−p0)=0.09\sigma^2 = p_0(1-p_0) = 0.09σ2=p0​(1−p0​)=0.09. Take α=0.05\alpha = 0.05α=0.05 (two-sided, z0.975=1.96z_{0.975} = 1.96z0.975​=1.96) and power 0.80.80.8 (z0.8=0.84z_{0.8} = 0.84z0.8​=0.84):

n≈2×(1.96+0.84)2×0.09(0.01)2=2×7.84×0.090.0001≈14,112 per armn \approx \frac{2 \times (1.96 + 0.84)^2 \times 0.09}{(0.01)^2} = \frac{2 \times 7.84 \times 0.09}{0.0001} \approx 14{,}112 \text{ per arm}n≈(0.01)22×(1.96+0.84)2×0.09​=0.00012×7.84×0.09​≈14,112 per arm

For unequal allocation (90% control / 10% treatment to limit risk), effective nnn drops on the smaller arm — adjust formulas or use software; don't naively plug 10% into a 50/50 calculator. Continuous metrics (session length): plug sample variance s2s^2s2 from pilot data for σ2\sigma^2σ2. Pilot an A/A week to estimate variance when historical buckets lie.

Interview angle

Hand-waving "two weeks is enough" fails. Walk the formula: state α\alphaα, power, MDE, plug p(1−p)p(1-p)p(1−p) or s2s^2s2, round up, mention CUPED if they use pre-period covariates.

Memory hook

Bigger δ\deltaδ, smaller nnn. Noisier metric (larger σ2\sigma^2σ2), bigger nnn. Higher power, bigger nnn.

#Which test: z, t, Mann–Whitney, bootstrap

Situation Test Why
Large nnn, mean or proportion Two-sample z-test CLT → normal statistic; use pooled SE for proportions
Small nnn, roughly normal metric Welch's t-test Unequal variances; uses t distribution
Heavy tails, ordinal, outliers Mann–Whitney U Ranks only; tests stochastic dominance, not mean
Weird shape, complex estimators Bootstrap on the statistic Resample users, rebuild δ^\hat\deltaδ^, empirical CI

For proportions, z-tests on p^\hat pp^​ are standard at product scale. For revenue per user, means are skewed — consider trimming, log transform, or bootstrap CIs. Multiple arms → ANOVA or pairwise with multiplicity control.

Rapid fire — Tests

z for big-nnn proportions/means; Welch t for small-nnn means; Mann–Whitney when ranks beat means; bootstrap when the estimator is ugly. Always cluster at the randomization unit when resampling.

#Ratio metrics and the delta method

Many product metrics are ratios: Rˉ=Xˉ/Yˉ\bar R = \bar X / \bar YRˉ=Xˉ/Yˉ (clicks per impressions, revenue per session). The ratio of two sample means is not Gaussian with a simple SE. The delta method linearizes around (μX,μY)(\mu_X, \mu_Y)(μX​,μY​):

Var(Xˉ/Yˉ)≈1μY2Var(Xˉ)+μX2μY4Var(Yˉ)−2μXμY3Cov(Xˉ,Yˉ)\mathrm{Var}(\bar X / \bar Y) \approx \frac{1}{\mu_Y^2}\mathrm{Var}(\bar X) + \frac{\mu_X^2}{\mu_Y^4}\mathrm{Var}(\bar Y) - \frac{2\mu_X}{\mu_Y^3}\mathrm{Cov}(\bar X, \bar Y)Var(Xˉ/Yˉ)≈μY2​1​Var(Xˉ)+μY4​μX2​​Var(Yˉ)−μY3​2μX​​Cov(Xˉ,Yˉ)

Plug sample estimates, get a z-statistic on the lift in Rˉ\bar RRˉ. Alternatively, bootstrap at user level with (Xi,Yi)(X_i, Y_i)(Xi​,Yi​) pairs — often more robust in practice. Linearization (CUPED-style) on user-level ratios is another production trick.

Interview angle

"How do you test revenue per visit?" — never treat per-visit rows as i.i.d. if randomization is per user; aggregate to user numerators/denominators, then delta method or bootstrap.

#Variance reduction: CUPED

CUPED (Controlled-experiment Using Pre-Experiment Data) subtracts a baseline covariate correlated with the outcome. For user-level metric YYY and pre-period covariate XXX (pre-experiment engagement):

θ=Cov(Y,X)Var(X),Y′=Y−θ(X−E[X])\theta = \frac{\mathrm{Cov}(Y, X)}{\mathrm{Var}(X)}, \qquad Y' = Y - \theta(X - \mathbb{E}[X])θ=Var(X)Cov(Y,X)​,Y′=Y−θ(X−E[X])

Analyze Y′Y'Y′ instead of YYY. If XXX is strongly predictive, Var(Y′)≪Var(Y)\mathrm{Var}(Y') \ll \mathrm{Var}(Y)Var(Y′)≪Var(Y), so the same MDE needs fewer users. θ\thetaθ is fit on pre-experiment data only (or control-only during the test) so you don't inject treatment into the variance reduction.

Memory hook

CUPED = "remove the part of the metric you already knew from before the test."

#Pitfalls and failure modes

#Peeking and sequential testing

Checking significance daily and stopping when p<0.05p < 0.05p<0.05 inflates Type I error badly — you're multiple-testing over time. Fixes: fixed-horizon analysis at precomputed nnn; or valid sequential rules (e.g. O'Brien–Fleming, always-valid p-values, Bayesian monitoring with calibrated priors). Never "stop when it looks good" without a plan.

#Multiple comparisons

K secondary metrics or K variants → chance of a false positive grows. Bonferroni: use α/K\alpha/Kα/K per test — conservative. Benjamini–Hochberg (FDR): sort p-values p(1)≤⋯≤p(m)p_{(1)} \le \cdots \le p_{(m)}p(1)​≤⋯≤p(m)​; find largest kkk with p(k)≤kmαp_{(k)} \le \frac{k}{m}\alphap(k)​≤mk​α; reject hypotheses 1,…,k1,\ldots,k1,…,k. BH controls false discovery rate — among rejected nulls, the expected fraction of false rejections is bounded by α\alphaα.

Worked BH example (m=4m=4m=4 secondary metrics, α=0.05\alpha=0.05α=0.05): sorted p-values 0.01,0.03,0.04,0.200.01, 0.03, 0.04, 0.200.01,0.03,0.04,0.20. Compare to kmα\frac{k}{m}\alphamk​α: k=1⇒0.0125k=1 \Rightarrow 0.0125k=1⇒0.0125 — 0.01≤0.01250.01 \le 0.01250.01≤0.0125 ✓; k=2⇒0.025k=2 \Rightarrow 0.025k=2⇒0.025 — 0.03>0.0250.03 > 0.0250.03>0.025 ✗; k=3⇒0.0375k=3 \Rightarrow 0.0375k=3⇒0.0375 — 0.04>0.03750.04 > 0.03750.04>0.0375 ✗; k=4⇒0.05k=4 \Rightarrow 0.05k=4⇒0.05 — 0.20>0.050.20 > 0.050.20>0.05 ✗. The largest passing kkk is 1, so reject only hypothesis 1. BH is step-up: check every kkk, not just until the first failure — had p(3)p_{(3)}p(3)​ been 0.0350.0350.035, hypotheses 1–3 would all be rejected even though p(2)p_{(2)}p(2)​ failed its own threshold. Pre-specify families of hypotheses (engagement vs revenue) so post-hoc storytelling does not masquerade as discovery.

#Sample ratio mismatch (SRM)

If you intended 50/50 split but observed 52/48, assignment may be broken (bucketing bug, bot traffic, eligibility filters). Check with a chi-square goodness-of-fit test on assignment counts; an SRM invalidates the experiment — debug before interpreting lifts.

#Novelty, primacy, and learning effects

Novelty: users click new UI because it's new. Primacy: power users hate change. Run longer or segment new vs returning. Interference / network effects: one user's treatment affects another (rideshare pricing, social feeds). Use cluster randomization, geo holdouts, or switchback designs alternating treatment by time window — with care for diurnal patterns.

#Simpson's paradox

A treatment can win within every segment but lose aggregated (or the reverse) when segment sizes differ. Classic illustration: a new ranker wins on mobile and desktop separately but loses overall because treatment traffic shifted toward a lower-converting segment. Always slice by platform, country, or cohort when interpreting; pre-specify segments to avoid fishing.

#Switchback and cluster designs (sketch)

Cluster randomization: assign whole markets or schools to treatment — correlation within cluster inflates variance; use cluster-robust SEs or cluster-based sample size calculators. Switchback: alternate treatment and control by time window (e.g. hour blocks) so both sides see mixed conditions — reduces marketplace interference at the cost of autocorrelation in the time series. Analyze with time-aware models or paired contrasts across adjacent windows; watch day-of-week confounds.

Launch on paradoxical aggregates

If overall lift is negative but every country is positive, you may be overweighting a shrinking segment — fix weighting, don't blindly ship.

Rapid fire — Pitfalls

No peeking without sequential methods. Many metrics → FDR or Bonferroni. SRM chi-square → stop and debug. Novelty/primacy need time. Network effects need clusters or switchbacks. Simpson's paradox breaks naive aggregates.

#Interleaving for ranking systems

Classic A/B assigns users to "always control" or "always treatment" ranker — high variance for noisy click metrics. Interleaving merges ranked lists so one result page shows a blend of both systems' orderings (e.g. team-draft interleaving). Clicks on interleaved slots attribute preference directly between rankers with less traffic than full A/B. Offline NDCG/MAP/MRR still pre-screens; interleaving is a sensitive online pairwise comparison before a full deployment. Pair with recommender systems thinking.

The DCG formula behind offline NDCG discounts position:

DCG@k=∑i=1k2reli−1log⁡2(i+1),NDCG@k=DCG@kIDCG@k\mathrm{DCG@k} = \sum_{i=1}^{k} \frac{2^{rel_i} - 1}{\log_2(i+1)}, \qquad \mathrm{NDCG@k} = \frac{\mathrm{DCG@k}}{\mathrm{IDCG@k}}DCG@k=i=1∑k​log2​(i+1)2reli​−1​,NDCG@k=IDCG@kDCG@k​

Online interleaving does not replace this — it answers a different question: which ranker earns the click on a blended page? Full A/B still validates business metrics (revenue, retention) after a ranker wins an interleaving duel.

Rapid fire — Interleaving

High sensitivity, low traffic for ranker A vs B. Team-draft builds fair merged lists. Offline NDCG uses graded relevance + log discount. Interleaving ≠ full product test — run both.

#Multi-armed bandits vs fixed A/B

A/B is pure explore-then-exploit: fixed allocation until nnn, then pick a winner — best for clean causal estimates and stakeholder trust.

Bandits adapt allocation toward better arms during the test (Thompson sampling: for each arm maintain a posterior on conversion rate Beta(α0+successes,β0+failures)\mathrm{Beta}(\alpha_0+\text{successes}, \beta_0+\text{failures})Beta(α0​+successes,β0​+failures); each step sample θa\theta_aθa​ from each posterior and allocate traffic to the highest draw). Higher short-term reward (lower cumulative regret) but biased estimates if you need an unbiased lift for a launch memo — the final arm allocation is not 50/50. Explore/exploit framing: A/B explores then exploits at the end; bandits explore continuously. Use bandits when regret during the test is costly (ad creative, headlines); use fixed A/B when inference rigor, parallel guardrails, and clean causal reporting matter.

Interview angle

"Bandit or A/B?" — If the question is "what's the causal lift with a reportable p-value?" → A/B. If "maximize reward while learning?" → Thompson sampling or ε-greedy, with awareness that inference is harder.

#Reading results and launch decisions

A disciplined read:

  1. Primary metric: CI on lift, practical significance vs MDE, ppp with correct interpretation.
  2. Guardrails: any regression beyond noise?
  3. Slices: stable across segments or Simpson warning?
  4. Quality checks: SRM, duration vs novelty window, AA tests passed earlier.
  5. Ship decision: launch, iterate, or kill — document opportunity cost of not shipping.

If offline and online disagree, post-mortem distribution shift, metric definition mismatch, and interference before retraining alone.

#Practical vs statistical significance

A metric can be statistically significant (tiny p-value) but practically irrelevant — a 0.02% conversion lift at massive nnn may not pay for engineering cost. Conversely, an underpowered test may fail to reject when the true lift is worthwhile. Report confidence intervals on business units (revenue per user per week) and compare the lower bound to a pre-defined minimum launch bar. Bias-variance thinking applies: noisy metrics need longer runs; overly precise peeking creates false certainty.

#Bootstrap procedure (user-level)

For skewed revenue: for each bootstrap replicate, resample nnn users with replacement, compute mean revenue in control and treatment arms, store the difference; repeat BBB times (e.g. B=10,000B=10{,}000B=10,000). The 2.5%–97.5% quantiles of differences form an approximate 95% CI. This respects user clustering and avoids normality assumptions. Same logic applies to bootstrap percentile tests on any smooth statistic — ratio metrics benefit from paired user resampling when users appear in both arms is impossible (only one arm per user).

Go deeper (optional)

CUPAC combines covariate adjustment with post-stratification; difference-in-differences handles geo rollouts when a full randomized experiment is politically impossible — know the identifying assumptions before citing them in an interview.

Rapid fire — Launch

Primary + CI + practical δ\deltaδ. Guardrails green. Segments consistent. No SRM, no peeking sin. Document kill/ship and monitor post-launch (ML in production).

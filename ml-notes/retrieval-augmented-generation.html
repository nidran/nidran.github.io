Retrieval-Augmented Generation (RAG)

Ground the model in evidence you control instead of whatever it memorized in pretraining.

Retrieval-augmented generation answers user questions by retrieving relevant documents, then generating conditioned on that context. It attacks the three production headaches of raw LLMs: knowledge cutoff, hallucination, and unverifiable claims. Done well, you get cite-able answers and cheaper updates than retraining—swap the index, not the weights.

What you'll be able to say after this chapter
  • Draw the RAG pipeline from ingestion to grounded answer and name where latency and quality trade off.
  • Choose chunking, embedding training (bi-encoder + InfoNCE), and ANN vs sparse retrieval—and when to hybrid with BM25 and rerank with a cross-encoder.
  • Split evaluation into retrieval (recall@k, MRR, NDCG) vs generation (faithfulness, relevance)—and point to LLM Eval for the full rubric.
  • Diagnose failure modes (bad chunks, wrong docs, lost-in-the-middle) and pick fixes from a systems table.
  • Contrast RAG vs fine-tuning vs long context for facts, freshness, and cost.

#Why RAG exists

Parametric knowledge in an LLM is implicit, static (training cutoff), and uncalibrated—the model sounds equally sure when wrong. RAG externalizes knowledge into a corpus you can version, audit, and delete. Product wins:

  • Freshness — re-index docs hourly; no full retrain.
  • Attribution — show sources; users trust and verify.
  • Hallucination control — when retrieval is good, you can measure faithfulness to context (see Hallucination).
  • Cost — updating facts via FT or continued pretrain dwarfs embedding + index maintenance for many enterprise KBs.

RAG does not replace alignment or instruction following; it feeds the evidence slot in a prompt assembled by your orchestration layer (LLM Inference, Decoding Strategies). Treat the retriever as a recall subsystem with its own SLIs—never as a black box bolted onto an otherwise unchanged chatbot.

Memory hook

Weights = fuzzy memory. Index = filing cabinet with page numbers.

Interview angle

Weak: "RAG searches Google then GPT answers." Strong: bi-encoder retrieval over chunked embeddings, optional sparse hybrid + cross-encoder rerank, context assembly with faithfulness eval—FT only when behavior must change, not when a PDF updated.

#Pipeline overview

flowchart LR
  A[Documents] --> B[Ingest & chunk]
  B --> C[Embed]
  C --> D[(Vector index)]
  Q[User query] --> E[Query rewrite / HyDE]
  E --> F[Retrieve top-k]
  D --> F
  F --> G[Rerank]
  G --> H[Assemble context]
  H --> I[LLM generate]
  I --> J[Answer + citations]
  F --> K[Sparse BM25]
  K --> L[Hybrid merge RRF]
  L --> G

Stages map cleanly to ownership: data engineering (ingest/chunk), search (embed/index/retrieve), and LLM (prompt + decode). Latency budgets usually spend 30–60% on retrieval+rereank, 40–70% on generation for single-hop QA.

#Production concerns beyond the diagram

  • Versioned indexes — blue/green re-embed when the encoder changes; never mix incompatible vector spaces in one index.
  • Access control — filter by tenant_id / ACL at retrieval time; the LLM must never see unauthorized chunks.
  • Caching — embed frequent queries; cache reranker results for head traffic.
  • Observability — log retrieved chunk IDs with each answer for replay when users flag wrong responses.
  • Prompt injection — untrusted docs are attackers; delimit untrusted text, strip instructions, and optionally run a lightweight harmful-instruction detector on retrieved content.
Rapid fire — Why & shape

RAG fixes cutoff, hallucination risk, and missing citations. Cheaper factual updates than FT. Pipeline: ingest → chunk → embed → index → retrieve → (rerank) → prompt → generate. Hybrid adds BM25 for lexical matches. Evaluate retrieval and generation separately (LLM Eval).

#Ingestion and chunking

Ingestion parses PDFs, HTML, tickets, slides into clean text—respect structure (headings, tables) where possible. Metadata (title, section, ACL, timestamp) travels with each chunk for filtering and citations.

Chunking is the silent killer of recall. Tradeoffs:

Strategy How When it helps
Fixed token windows 256–512 tokens, overlap 10–20% Simple baseline; overlap reduces boundary cuts
Structure-aware Split on headings / paragraphs Docs, policies, wikis
Semantic Embed sentences; merge until similarity drops Variable-density notes
Parent–child Small child chunks for search; parent for context Need precise hit + wide context

Too small → fragments lose meaning. Too large → dilute embedding, waste context window, bury the answer (lost-in-the-middle: models under-attend to middle chunks in long prompts).

Rule of thumb: start 384–512 tokens with 50–80 token overlap on English prose; shrink for structured logs, grow for legal contracts where sentences chain across pages. Validate by sweeping chunk size on retrieval recall@k—optimum is rarely the first guess.

Metadata for filtering — date, product SKU, geography, doc type—lets you run faceted retrieval ("only policies effective in 2024") before vector search, improving precision without touching the LLM.

Common mistake

Embedding entire 10-page PDFs as one vector—retrieval returns the right file but the generator still cannot find the sentence.

Memory hook

Chunk for the retriever's eye; parent doc for the generator's brain.

#Embeddings and indexing

#Bi-encoders vs cross-encoders

A bi-encoder maps query qqq and document ddd independently:

s(q,d)=sim(f(q),g(d))s(q,d) = \mathrm{sim}\big(f(q), g(d)\big)s(q,d)=sim(f(q),g(d))

typically cosine after L2-normalization (dot product on unit vectors). Encode all documents offline, store in a vector database—query time is one embedding + ANN search. See Embeddings & Vector Search and Two-Tower Retrieval.

A cross-encoder jointly encodes [q;d][q;d][q;d] through a transformer and outputs a scalar relevance score. Accurate for reranking tens of pairs, impossible for millions without a first stage.

#Contrastive training (InfoNCE)

Train f,gf,gf,g so positives are close and negatives far. With temperature τ\tauτ,

LInfoNCE=−log⁡esim(q,d+)/τ∑kesim(q,dk)/τ\mathcal{L}_{\text{InfoNCE}} = -\log \frac{e^{\mathrm{sim}(q,d^+)/\tau}}{\sum_k e^{\mathrm{sim}(q,d_k)/\tau}}LInfoNCE​=−log∑k​esim(q,dk​)/τesim(q,d+)/τ​

In-batch negatives are cheap; add hard negatives (BM25 top misses that are wrong) to avoid collapse. Same family as ranking losses in Loss Functions (§embeddings). Domain mismatch (legal vs chat) needs finetune or adapters on your corpus.

Embedding API choice: off-the-shelf models (E5, BGE, GTE, OpenAI embeddings) are fine to prototype; production on private jargon usually needs contrastive finetune on (q,d+,d−)(q, d^+, d^-)(q,d+,d−) triples mined from click logs or SME-labeled pairs. Evaluate with the same recall@k slice you will gate in CI.

Two-tower symmetry: often f=gf=gf=g (shared weights) for queries and docs; asymmetric towers help when queries are short questions and docs are long passages (Two-Tower Retrieval).

#Score calibration and thresholds

Raw cosine scores are not probabilities. For abstention ("I don't know"), fit a validation score threshold or small calibrator so precision on answered queries meets SLO. Hybrid RRF sidesteps calibration for merging ranks but you still need thresholds for whether to answer at all.

#ANN indexes: HNSW, IVF, PQ

Exact nearest neighbor does not scale. Approximate methods trade recall for speed:

Index Idea Knobs Tradeoff
HNSW Graph greedy search M, efConstruction, efSearch High recall, RAM-heavy
IVF Cluster buckets, probe few nlist, nprobe Fast at scale; needs training
PQ Compress vectors subquantizers Saves RAM; hurts recall

Tune until recall@k on a labeled dev set plateaus within latency SLO.

#Sparse BM25 and hybrid search

BM25 scores lexical overlap—excellent for SKUs, error codes, names dense retrievers miss. Hybrid: run dense + sparse, merge with reciprocal rank fusion (RRF):

RRF(d)=∑i1k+ranki(d)\mathrm{RRF}(d) = \sum_i \frac{1}{k + \mathrm{rank}_i(d)}RRF(d)=i∑​k+ranki​(d)1​

with constant kkk (often 60). No score calibration needed. Recommender Systems intuition: two weak experts, one rank list.

#Reranking, query rewriting, HyDE

Retrieve top 50–200, cross-encode down to 5–15. Query rewriting expands acronyms or decomposes multi-part questions. HyDE (hypothetical document embeddings): LLM drafts a fake answer, embed that to search—helps lexical mismatch when used cautiously (adds latency + hallucination risk in the draft).

Rapid fire — Retrieval stack

Bi-encoder: independent f(q),g(d)f(q), g(d)f(q),g(d); fast ANN. Cross-encoder: joint; rerank only. InfoNCE with in-batch + hard negs. ANN: HNSW/IVF/PQ recall–latency tradeoffs. BM25 + RRF hybrid. Rerank top-k'. HyDE/rewrite for query drift.

#Context assembly and generation

Pack reranked chunks into the prompt with clear delimiters, source titles, and (if possible) ordered by relevance with the best chunk near the start or end—not the middle—mitigating lost-in-the-middle. Instruct the model to cite chunk IDs and refuse when context is insufficient.

Prompt template sketch (interview whiteboard):

System: Answer only from CONTEXT. Cite [id] after each claim. Say "insufficient context" if needed.

CONTEXT:
[1] title: …\n<text>
[2] …

USER: <question>

Variants add JSON output for downstream apps or force bullet + citation formatting for support macros. Keep system and user roles consistent with how the base model was SFT'd (LLM Training).

Decoding choices matter: lower temperature for factual extracts; require quotes for high-stakes domains. Chain with tools (LLM Inference) when answers need arithmetic or live APIs in addition to RAG.

#Open vs closed domain

Setting Corpus Retrieval stance
Closed Fixed approved KB High precision; abstain aggressively
Open web Internet + crawls Hybrid + heavy safety filters
Internal + web Blended indexes Namespace separation; never mix ACLs

Closed-domain support bots should tune high precision@k even if recall suffers—wrong retrieved policy is worse than "I don't know."

#Data flywheel

Production RAG improves when you log queries, retrieved IDs, clicks, and thumbs-down. Hard negatives for embedding finetune come from "retrieved but user rejected." Golden sets grow from escalations. Without this loop, offline recall plateaus while user complaints climb.

Rapid fire — Generation & ops

Delimit CONTEXT; cite IDs; abstain instruction. Best chunks at edges against lost-in-the-middle. Lower temperature for facts. Closed domain = precision over recall. Log retrieval for hard-negative mining. LoRA teaches cite-format, not the facts themselves.

Interview angle

If they probe context limits: retrieval quality dominates—stuffing 100k tokens of mediocre chunks loses to 8k of reranked gold.

#Evaluation

Split metrics—conflating them hides whether retrieval or generation failed.

#Retrieval

On queries with labeled relevant doc IDs:

  • Recall@k — fraction of queries with a hit in top kkk (Precision & Recall).
  • MRR — focuses on the rank of the first correct doc.
  • NDCG@k — graded relevance; see Ranking Metrics.

Improve recall before touching the LLM.

Worked retrieval example (conceptual). Ten test queries; relevant doc appears in top-3 for seven queries → Recall@3 = 0.7. If the first relevant doc ranks 1,1,4,2,1,9,1,… positions, MRR averages 1/rank1/\text{rank}1/rank. NDCG adds graded labels ("partially relevant" vs "perfect"). Report per-domain slices—support tickets often need higher kkk than executive FAQs.

#Generation

Reference-free checks aligned with LLM Eval:

  • Faithfulness / groundedness — answer entailed by provided context?
  • Answer relevance — addresses the question?
  • Context relevance — were retrieved chunks on-topic?

Human side-by-side still gold for tone; LLM-as-judge scales regression tests.

Pair with standard Model Evaluation & Validation hygiene: fixed dev/test splits, no query leakage from train chunks, and regression gates in CI when you change embedders.

Memory hook

Retrieval metrics = did we fetch the right page? Generation metrics = did we read it honestly?

#Building the system: latency and cost

Typical single-hop Q&A serving path (numbers are illustrative):

Stage Latency share Cost driver
Query embed 5–15 ms GPU batching
ANN search 10–40 ms index RAM, efSearch
BM25 (optional) 5–20 ms inverted index size
Cross-encoder rerank 50–200 ms pairs × GPU
LLM generation 0.5–3 s output tokens

If reranking dominates, cap candidates (50 not 500) or distill to a smaller cross-encoder. If generation dominates, shorten context (fewer chunks) after you have verified recall—never cut retrieval budget first without metrics.

Batch vs stream: retrieval can batch across users; generation often streams tokens. Separate autoscaling: search tier (CPU/GPU hybrid) vs LLM replica pool.

#Failure modes and fixes

Symptom Likely cause Fix
Confident wrong answer Retrieval miss + no abstain Hybrid search, query rewrite, raise kkk, reranker
Answer ignores docs Prompt/format; middle placement Delimiters, move best chunk to edges, cite-or-abstain instruction
Contradictory sources Stale/conflicting chunks Metadata filters, recency boost, de-dup index
Right doc, wrong span Chunk too large Smaller chunks + parent summary

Works in English only Monolingual embeddings Multilingual encoder or translate pipeline

Rapid fire — Eval & failures

Recall@k, MRR, NDCG on retrieval. Faithfulness + relevance on generation (LLM Eval). Missed retrieval → hybrid + rerank. Ignored context → prompt + lost-in-the-middle placement. Stale index → versioning. ACL at retrieve time, not post-hoc.

#Agentic, multi-hop, and GraphRAG

Multi-hop RAG iterates: decompose question, retrieve subqueries, aggregate—agent loops tie to tool eval in LLM Eval. A classic pattern is ReAct-style: the model emits a search query, reads chunks, then decides the next hop. Risks: error compounding (wrong hop-1 doc poisons hop-2), cost explosions (each hop = retrieve + LLM), and eval difficulty (credit assignment per hop). Mitigations: max-hop limits, confidence gating ("stop if score <<< threshold"), and logging intermediate queries for human review.

GraphRAG builds a knowledge graph (entities, relations) over the corpus for global questions ("themes across 10k tickets") where flat chunk search fails. Community summaries on graph clusters support questions like "what are the recurring outage causes?" without retrieving 50 random chunks. Heavier offline build (entity extraction, resolution, graph layout); wins on holistic synthesis over connected evidence, not factoid lookup.

Briefly: default to single-hop RAG until benchmarks prove multi-hop; add graphs when queries are inherently relational or require aggregate themes across many documents.

Interview angle

"Design enterprise RAG" — narrate ACL-aware ingest, hybrid retrieval, rerank, cite-or-abstain prompt, split eval dashboards, and rollout via offline recall before online A/B—not "we'll fine-tune GPT on all PDFs."

#RAG vs fine-tuning vs long context

Approach Best for Weakness
RAG Fresh facts, citations, many docs Retrieval errors; latency; orchestration
Fine-tune / LoRA Style, format, domain reasoning patterns Catastrophic forgetting; stale facts; cost ([[llm-training-and-alignment
Long context Many docs already in prompt; simpler stack Quadratic attention cost; still attends poorly mid-context; no automatic cite

Practical stacks combine: RAG for evidence, modest LoRA for tone, long context for conversation history—not for whole corpora.

When long context displaces RAG: code assistants with open files in-repo, multi-turn legal review where the user pastes exhibits, or "chat with this one PDF" under ~100 pages. When the corpus is many documents, dynamic, or needs citations, RAG remains cheaper and more honest than stuffing context.

Fine-tuning complementary role: LoRA on (instruction, grounded answer) pairs teaches citation format and abstention given retrieved text in the prompt—it does not replace the index. Full FT to memorize product specs goes stale the week pricing changes.

Go deeper (optional)

Compression retrievers (LLMLingua), late interaction models (ColBERT), and learnable sparse-dense hybrids blur the clean bi-encoder story—mention if the role is search ML, not just LLM glue.

#ColBERT and multi-vector retrieval (sketch)

Classic bi-encoders compress a whole passage into one vector—cheap but lossy. ColBERT keeps a vector per token and scores with a late interaction (MaxSim): match query tokens to document tokens, sum best hits, then aggregate. You store more vectors per doc but retrieve with two-stage pruning. Interview one-liner: ColBERT trades index size for finer overlap signals between query spans and doc spans—strong on keyword overlap inside long passages.

#Security checklist for interviewed designs

  1. Untrusted content is input — retrieved text can say "ignore previous instructions."
  2. Sanitize — XML/JSON delimiters; optional secondary classifier on chunks.
  3. Grounding eval in CI — faithfulness regression on adversarial chunks that tempt override.
  4. Least privilege — retrieval service credentials cannot exfiltrate unrelated tenants.
  5. Citation verification — post-check that cited IDs appear in the prompt and support the claim (lightweight string/NLI).

These sit alongside model-level alignment (LLM Training)—RAG security is systems security.

Interview closure sentence: "I'd ship single-hop hybrid RAG with rerank, cite-or-abstain prompting, split retrieval and faithfulness evals per LLM Eval, and only fine-tune adapters for tone—not for facts." That single sentence shows you understand the full stack end to end, from index freshness to grounded generation.

Rapid fire — Advanced & security

ColBERT: multi-vector late interaction, better span overlap, bigger index. Prompt injection via corpus is real; delimit and test. Citation verify in post-processing. Closed ACL at retrieve. Flywheel: logged rejects → hard negatives.

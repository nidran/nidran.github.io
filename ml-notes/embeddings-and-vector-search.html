Embeddings & Vector Search

Say it in 30s: An embedding maps text (or images, queries, items) into a fixed dense vector so that semantic similarity becomes cosine distance or dot product. Bi-encoders embed query and document separately—fast because you pre-index documents—while cross-encoders score query–document pairs jointly and are accurate but too slow for millions of docs. Training uses contrastive losses (InfoNCE): pull a positive pair together, push negatives apart in a batch. At scale you retrieve with ANN indexes (HNSW, IVF+PQ) that trade a little recall for sub-millisecond latency.

Key points

  • Pooling: mean/max over token vectors, or use the [CLS] / last token for sentence-level reps; L2-normalize if using cosine via dot product.
  • InfoNCE: −log⁡esim(q,d+)/τ∑kesim(q,dk)/τ-\log \dfrac{e^{\mathrm{sim}(q,d^+)/\tau}}{\sum_k e^{\mathrm{sim}(q,d_k)/\tau}}−log∑k​esim(q,dk​)/τesim(q,d+)/τ​—in-batch negatives are free but biased; hard negative mining fixes easy-batch collapse.
  • Hybrid search: dense + BM25, merged with reciprocal rank fusion (RRF)—sparse catches exact entities dense misses.
  • ANN knobs: HNSW efConstruction/M (recall vs build time); IVF nlist/nprobe; PQ compresses vectors at recall cost.

Common follow-ups / traps

  • "Bi- vs cross-encoder?" → bi-encoder for candidate generation @ millions; cross-encoder to rerank top 50–200.
  • "Why normalize?" → dot product on unit vectors equals cosine; stabilizes training and indexing.
  • "Metric at interview?" → recall@k on retrieval, MRR when one right doc matters, NDCG when grades differ—see Ranking Metrics.

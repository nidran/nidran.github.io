KV Cache

Say it in 30s: Autoregressive decoding would recompute keys and values for all past tokens at every new step — wasteful. A KV cache stores, per layer, the KKK and VVV projections for tokens already processed; each decode step only runs the new token through the stack and appends to the cache. Memory grows linearly with context length; that footprint is often the serving bottleneck, which is why GQA/MQA share KV heads across query heads.

Key points

  • Cached tensors: for each layer, K,V∈Rbatch×heads×seq_len×dheadK,V \in \mathbb{R}^{\text{batch} \times \text{heads} \times \text{seq\_len} \times d_{\text{head}}}K,V∈Rbatch×heads×seq_len×dhead​.
  • Memory (order of magnitude): 2×L×Hkv×dhead×seq_len×batch×bytes2 \times L \times H_{\text{kv}} \times d_{\text{head}} \times \text{seq\_len} \times \text{batch} \times \text{bytes}2×L×Hkv​×dhead​×seq_len×batch×bytes (factor 2 = KKK and VVV).
  • Prefill computes cache for the prompt in one parallel pass; decode is one token at a time, mostly reading cache.
  • Queries are not cached — only KKK and VVV are reused when attending from the new position.
  • Quantized KV (INT8/FP8) trades accuracy for capacity; PagedAttention (vLLM) maps logical cache to non-contiguous GPU pages.

Common follow-ups / traps

  • "Why not cache QQQ?" → each step's query is new; past keys/values are fixed given past hidden states.
  • "GQA vs MQA?" → grouped-query attention: several Q heads share one KV head; multi-query: one KV head for all Q heads — bigger KV savings, some quality loss.
  • "Does cache change training?" → no — training is parallel over full sequence; cache is an inference-only optimization.

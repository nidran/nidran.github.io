ML in Production: Serving, Monitoring & MLOps

Training is a batch job; production is a streaming system with customers attached — skew, drift, and delayed labels are the default, not the exception.

Shipping a model is the beginning. The interview version of MLOps is not a tool name-drop checklist — it is the ability to trace a user request through features, model version, business metric, and back to the training data snapshot that produced the weights, then say what you would check when any link in that chain weakens. The failure modes that dominate mature teams are not "wrong architecture" but training-serving skew, point-in-time violations in the feature store, silent drift, and metrics that look fine while revenue moves. This chapter covers inference modes, deployment patterns, registries and reproducibility, drift taxonomy and detection (including PSI), retraining strategy, latency/cost levers, fairness checks, and an incident playbook when live metrics drop. Pair with ML System Design Framework and Model Evaluation & Validation.

What you'll be able to say after this chapter
  • Choose batch vs online vs streaming inference from latency and freshness requirements.
  • Define point-in-time correctness and list three causes of training-serving skew.
  • Compare shadow, canary, blue/green, and A/B deployment with rollback triggers.
  • Separate covariate shift, prior shift, and concept drift — and name PSI, KS, and KL/JS as detectors.
  • Explain delayed labels, proxy metrics, and when scheduled vs triggered retrain wins.
  • Walk the incident checklist when production metrics drop without panicking.

#Inference modes: batch, online, streaming

Batch inference scores a large corpus on a schedule (nightly ad propensities, churn scores for CRM). Pros: cheap amortization, heavy models OK. Cons: scores stale until the next run — bad when events matter in minutes.

Online (real-time) inference computes predictions per request with a latency SLO (p99 < 100ms common for ranking/ads). Needs feature serving from caches/stores, horizontal autoscaling, and often model distillation or smaller architectures.

Streaming inference updates features and sometimes model state on an event stream (Kafka → Flink). Use when features are volatile (last-5-minute clicks) or when you fuse batch baselines with real-time deltas.

Mode Freshness Cost profile Typical use
Batch Hours–days Low $/prediction at scale Churn lists, catalog tags
Online Sub-second Per-QPS infra + cache Search rank, fraud score
Streaming Event-driven Pipeline ops + state Session features, counters

Hybrid lambda/kappa patterns are the norm: batch user embeddings daily, stream session counters per request, merge at the ranker.

Request path (mental model). Client → API gateway → feature fetch (parallel RPCs) → model server (batched GPU) → post-processing (calibration, business rules) → response. Each hop consumes budget; feature stores are often parallelized with a hard timeout — missing features fall back to defaults that must match training sentinels.

SLO example: p99 80ms rank, 99.9% availability, error budget 0.1%/week. Violations trigger autoscale, circuit breakers to a simpler model, or traffic shed to popularity fallback — state the fallback explicitly in interviews (rules beat a timing-out DCN).

Memory hook

Batch = cheap and stale; online = fresh and expensive; streaming = fresh features without scoring everything offline.

Interview angle

Ask latency and freshness before picking inference. Recsys at 100ms almost always means precomputed item side + online user side.

Rapid fire — Inference

Batch for scale and staleness tolerance. Online for request-time decisions with SLOs. Streaming for evolving counters/state. Most systems blend batch + real-time features.

#Feature stores and point-in-time correctness

A feature store serves the same feature definitions in training and serving, keyed by entity ID and timestamp. Point-in-time correctness means: for a label at time ttt, every feature must reflect only information available before ttt. Violations are Data Leakage — the model learns the future.

Implementation pattern: store feature snapshots or event-time aggregations with as_of joins in training SQL; in serving, read the latest committed feature vector up to request_time. Offline backfills must use the same transformation code path (often packaged as a shared library).

Typical layout: offline store (warehouse tables for training sets) + online store (Redis/Dynamo for low-latency reads) fed by the same stream processors. Time-travel APIs let researchers request get_features(entity_id, timestamp=t) for backtests without rewriting SQL.

Concern Training Serving
Join key (user_id, event_time) (user_id, request_id)
Aggregation window Closed intervals ending at label time Rolling "as of now"
Freshness Backfill OK SLO-driven (seconds–hours)

Feature ownership matters organizationally: central platform teams ship transforms; product teams own entity definitions. Version features in the model registry next to weights so rollback reverts both.

Common mistake

Joining "current user profile" to historical labels — profiles were updated after the label event; offline metrics inflate.

#Training-serving skew

Skew is any systematic difference between the distribution or computation of features at train vs serve time.

Cause Example Fix
Different code paths Python training, Java serving Shared feature lib; CI contract tests
Missing defaults Null imputation differs Explicit default sentinel; monitoring
Logging vs live features Trained on stale batch only Serve what you logged; parity checks
Normalization drift Stats from old window Versioned stats; refresh job
Candidate universe Train on exposed items only Importance weight or multi-stage replay

Prevention: snapshot serving features in logs, daily train-serve parity jobs comparing distributions, and shadow mode deployment (see below). Deep dive card: Training-Serving Skew.

Add golden request tests: replay recorded production payloads through offline transform code and assert bitwise or epsilon equality on numerics before each release. This catches the subtle bugs — timezone on "day of week," off-by-one in sequence windows, off-by-float in embedding norms — that dashboards miss until revenue moves.

For ranking, log the candidate set ID list and retrieval scores at serve time so offline replay evaluates the same slate distribution the ranker saw live; retraining on reshuffled candidates without matching retrieval is a silent skew source.

Rapid fire — Skew

Same transforms, same defaults, same time semantics. Log served features for training replay. Parity tests between offline batch and online RPC.

#Deployment patterns and rollback

Shadow deployment: new model runs in parallel, predictions discarded or compared — zero user risk; validates latency and skew.

Canary: small % of traffic on new model; watch error rate, latency, business metrics; auto-rollback on breach.

Blue/green: two full stacks; instant switch; rollback = flip traffic back — good when infra allows duplicate capacity.

A/B test: randomized experiment for causal metric lift — required when claiming improvement, not just safety. See A/B Testing & Experimentation.

Rollback triggers: SLO latency regression, error spikes, guardrail metrics (fraud FP, toxicity reports), and pre-agreed business KPI floors. Keep previous model version hot in the registry.

Experimentation ethics: ramp canaries slowly on revenue-critical paths; pre-define duration and stopping rules to avoid p-hacking. When offline and online disagree, trust online for product metrics but mine offline for regression localization (which slice broke).

For batch systems, deployment is often pointer flip on output tables (Blue dataset / Green dataset) with downstream consumers reading versioned paths — same conceptual pattern as online blue/green.

Memory hook

Shadow = observe; canary = trust a little; blue/green = switch; A/B = prove causally.

Rapid fire — Deploy

Shadow for parity; canary for gradual risk; blue/green for fast revert; A/B for proof. Roll back on latency, errors, guardrails — not vibes.

#Model registry, versioning, reproducibility

A model registry stores artifacts: weights, feature manifest, training data hash, hyperparameters, metrics, and approval state. Semantic versioning or content hashes tie a served endpoint to an immutable artifact.

Reproducibility checklist: seed control, pinned dependencies, logged data snapshots, git SHA of training code, and documented data filters (time windows, bot removal). For regulated domains, retain lineage from prediction → model version → training set.

Promotion workflow. Train job completes → offline metrics on holdout → comparison to champion → human approval for high-risk domains → artifact upload → integration tests (schema of features, max latency dry-run) → canary deploy. Reject promotion if slice regressions appear even when global AUC rises — a classic fairness and robustness trap.

Champion/challenger terminology: production serves champion; challenger runs in shadow or small canary until statistically significant lift on pre-registered metrics. Document minimum detectable effect so you do not ship noise.

Interview angle

Name the registry when asked "how do you roll back?" — "serve v42 from registry while v43 trains" beats vague "we keep old weights."

#Monitoring: drift, labels, and proxies

Production monitoring spans data, model, infrastructure, and business layers.

#Drift taxonomy

  • Covariate shift (data drift): P(X)P(X)P(X) changes; P(Y∣X)P(Y|X)P(Y∣X) stable — e.g. new user geography after marketing campaign.
  • Prior shift (label drift): P(Y)P(Y)P(Y) changes — e.g. fraud rate spikes in holiday season.
  • Concept drift: P(Y∣X)P(Y|X)P(Y∣X) changes — the same feature vector means something different (new fraud tactic, UI redesign).

Rule of thumb: PSI < 0.1 stable; 0.1–0.25 watch; > 0.25 investigate (thresholds vary by domain). PSI is one-dimensional — pair with multivariate tests and slice monitors (country, app version).

Prediction drift (score distribution shift) often precedes label drift — cheap early warning when labels are delayed.

Multivariate drift. Univariate PSI on 500 features triggers false alarms; use random projections, PCA subspace tests, or tree-based drift detectors (e.g. classifying "reference vs production" on features — AUC ≫0.5\gg 0.5≫0.5 means separable shift). In interviews, say you'd combine univariate PSI for alerting with multivariate triage on top movers.

#Delayed labels and proxy metrics

Fraud, churn, and LTV labels arrive days or weeks late. Operate on proxy metrics (click, session start) with known lag structure while backfilling true labels. Counterfactual evaluation on exploration traffic helps when logs are biased.

Interview angle

Strong: distinguish input drift from concept drift and say what you'd retrain vs what you'd revert (bad deploy vs world change).

Rapid fire — Monitoring

Covariate = P(X)P(X)P(X); prior = P(Y)P(Y)P(Y); concept = P(Y∣X)P(Y|X)P(Y∣X). PSI on binned features; KS on continuous; JS for scores. Prediction drift is the fast signal. Proxies when labels lag.

#Retraining strategies

Scheduled retrain (daily/weekly): simple ops; risks learning stale patterns between runs.

Triggered retrain when PSI/KS breaches, online metric drop, or data volume threshold — saves compute but needs automation.

Continual learning updates weights online; rare in regulation-heavy or non-stationary-tabular settings due to catastrophic forgetting and audit requirements — more common in ads with incremental linear models or small adapter updates.

Cadence trade-off: faster domains (short-video, ads) → daily + streaming features; slow domains (credit) → monthly with heavy validation.

Data volume triggers: retrain when new labeled volume crosses a threshold or when active learning queues human labels for uncertain slices — common in moderation and fraud.

Evaluation before promote: hold out the most recent time window (for time-series, never random split — see Time-Series Validation & Backtesting). For classifiers, check Precision & Recall at the production threshold, not only ROC-AUC vs PR-AUC.

#Observability and the feedback loop

Log request_id, model_version, feature_version, inputs (hashed or bucketed), outputs, and downstream outcomes when labels arrive. Pipelines: clickstream → label joiner → training table → registry → serve — close the loop deliberately, not accidentally amplifying bias.

Dashboards worth naming in interviews: feature null rate, score distribution, latency p50/p99, cache hit rate, GPU utilization, and business KPI by model slice. Alert on compound conditions (PSI high and CTR down), not single metrics alone.

Connect training to Regularization and data freshness: retraining on stale windows without reweighting recent events behaves like an overly strong prior.

#Latency and cost optimization

Levers interviewers recognize:

  • Distillation — teacher → student with softer targets (LLM Inference patterns apply at scale).
  • Quantization (INT8) and pruning for GPU/CPU throughput.
  • Caching — user embeddings, frequent queries, partial ranker outputs.
  • Batching — dynamic batching on GPU serving (TensorRT/Triton).
  • Two-stage — cheap retrieve, expensive rank on thousands not billions (see Recommender Systems).

Cost-aware serving picks model size to p99 latency, not mean — tail drives time-outs.

#Serving topologies

Embedded in app (mobile on-device): tiny models, INT8, no network — drift handled via OTA model bundle updates. Sidecar / microservice: language-agnostic RPC (gRPC), autoscaling replicas per model. Multi-model bin packing: Triton schedules heterogeneous models on shared GPUs. LLM-specific: continuous batching, prefix caching, speculative decoding — see LLM Inference; analogies (cache KV, batch requests) apply to rankers at smaller scale.

Testing before prod: contract tests on feature schemas, load tests at peak QPS, and chaos drills (feature store timeout → defaults). Load test the p99 tail, not average QPS alone.

Rapid fire — Efficiency

Distill, quantize, cache embeddings, batch GPU calls. Funnel cheap stages before expensive cross-models. Optimize p99, not average.

#Fairness and explainability checks

Pre-launch and ongoing: slice metrics (demographic, region, new vs power users), disparate impact on allocation rates (ads, loans, moderation), and explainability where regulated (SHAP on tabular, attention ≠ explanation for deep nets — state limits).

Fairness fixes intersect product policy: thresholds per slice, human review queues, and constraint optimization in re-ranking — not only "train a fairer model."

Explainability in interviews: for tree models, SHAP for local attributions; for deep models, admit limitations — surface-level attention weights are not faithful explanations. Regulated use cases may require adverse action notices tied to top features.

#Batch vs online retraining coordination

Many stacks run nightly batch retrain while serving hourly refreshed linear calibration layers on top — decouple slow full retrains from fast adapter updates. Document which artifact each layer reads so rollback does not leave mismatched pairs.

Rapid fire — MLOps loop

Log → label → feature store → train → evaluate → register → canary → monitor → trigger/schedule retrain. Version everything. Never promote without slice checks.

#Incident checklist: metrics dropped — what now?

Structured response beats retraining randomly:

  1. Confirm the signal — not a dashboard bug, seasonal weekday effect, or external outage (ads inventory, upstream API).
  2. Segment — which metric, which slice (platform, country, model version), start time vs deploy time.
  3. Infra — latency, error rate, feature store freshness, null rates on key features.
  4. Skew check — compare logged serve features to training distributions (PSI per feature).
  5. Model version — correlate with canary/rollback; if post-deploy, rollback first, analyze second.
  6. Data pipeline — broken ETL, changed schema, bot traffic spike.
  7. Concept drift — real world changed (competitor, UI test) → needs retrain or policy fix, not rollback.
  8. Communication — incident owner, ETA, guardrails if disabling ML fallback to rules.

Playbook extensions for ranking/recsys (ties to Recommender Systems): check retrieval ANN health (index version, empty recall), explore rate changes, and creator-level impression drops. For ads, verify auction inputs and calibration layer — metric drops may be revenue mix not model quality.

Post-incident: write a blameless note capturing detection gap (why PSI did not fire), fix (registry rollback vs retrain), and preventive monitor. Interviewers love hearing "we added a null-rate alert on feature X after incident Y."

Memory hook

Roll back deploys before you retrain the world.

Interview angle

Walk the checklist out loud — interviewers reward operational muscle, not "I'd retrain on more data."

Rapid fire — Incidents

Validate alert → slice → infra → feature PSI → version correlation → rollback if deploy → pipeline → concept drift → comms. Rollback beats blind retrain.

#Putting it together: ads click model slice

Walk a concrete path: training reads impression logs from the warehouse with point-in-time user stats; positives are clicks within 24h; features include creative embedding (batch), user segment (batch), and session counters (stream). Serving fetches the same three families from the online store; a logistic or shallow DNN runs at 30ms p99. Shadow a new GBDT champion against the live linear model; canary at 2% traffic; monitor CTR, revenue per mille, and PSI on bid floor features. Labels delay hours — early warning from predicted CTR distribution shift. Roll back if canary RPM drops beyond a pre-set guardrail while global latency stays green.

Rapid fire — End-to-end slice

Warehouse labels + streaming counters → shared transforms → registry versions → shadow → canary → PSI on inputs and scores → delayed label refresh → scheduled daily retrain.

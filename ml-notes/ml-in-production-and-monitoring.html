ML in Production & Monitoring

System Design: what happens after the offline metric looks good, and how a model stays good once real traffic reaches it.

A trained model is a small part of a production ML system. The surrounding pieces (data pipelines, serving, rollout, monitoring, retraining, governance) determine whether the offline gain survives contact with reality. This chapter complements ML System Design Framework, which covers how to scope and structure a design answer, by covering the operational half: how predictions are served, how rollouts are made safe, what to monitor, and what to do when something breaks.

What you'll be able to say after this chapter
  • Choose between batch, online, and streaming serving from latency, freshness, and cost requirements.
  • Explain training-serving skew, its common causes, and how feature stores and shared code reduce it.
  • Name the main latency and throughput levers and the tradeoff each one buys.
  • Sequence a safe rollout: offline checks, shadow, canary, A/B, with a rollback trigger.
  • Distinguish covariate shift, label shift, and concept drift, and say which monitors detect which (and which cannot).
  • Compute PSI and explain why KS and PSI alerts need judgment.
  • Define a retraining policy and the reproducibility artifacts that support it.

#Serving Patterns

Pattern How predictions are produced Latency Freshness Typical fit
Batch Score all (or all relevant) entities on a schedule; write results to a table or cache Reads are instant; staleness equals the schedule interval Hours to days Nightly churn scores, email targeting, candidate generation that tolerates staleness
Online (request-response) Model called synchronously per request with fresh features Tens to hundreds of milliseconds budget Seconds or less Fraud checks at payment time, search ranking, personalization
Streaming (near-real-time) Events processed continuously; features and/or scores updated as events arrive Sub-second to seconds from event to updated score Seconds Rolling behavioral features, anomaly detection on event streams, session-based recommendations
Edge / on-device Model runs on the client No network round trip Updated with app or model releases Privacy-sensitive, offline, or ultra-low-latency use cases

Many systems are hybrids: expensive user or item representations are computed in batch, cheap fresh signals are joined online, and a lightweight model combines them at request time. This is the common structure of multi-stage retrieval-and-ranking designs.

Selection logic:

  • If the decision does not depend on information newer than the batch interval, batch is generally the cheapest and simplest option, with the added benefit that outputs can be inspected before use.
  • If the input exists only at request time (the current query, cart, or transaction), online scoring is required for at least part of the model.
  • Streaming adds operational complexity (ordering, late events, state, exactly-once semantics), so it is justified when freshness measurably changes the outcome.
Interview angle

Anchor the choice in numbers: the latency budget, the QPS, the feature freshness the metric actually needs, and the cost per prediction. A common strong move is to ask "what is the accuracy lost per hour of staleness?" because that converts a vague freshness debate into a measurable tradeoff.

#Training-Serving Skew

Training-serving skew is a difference between the data or computation a model saw in training and what it receives in production. It is a leading cause of the offline-online gap, and unlike drift it is present from day one.

Cause Example Mitigation
Different code paths Features computed with SQL in training and re-implemented in a service for serving, with different handling of nulls or rounding One shared transformation library or definition used by both paths
Different data sources or freshness Training reads a warehouse snapshot that is later corrected; serving reads a live store with late or missing values Log the features exactly as served and train on those logged values
Time-travel errors Training features computed using data that would not have existed at that moment (see Data Preprocessing & Feature Engineering) Point-in-time correct joins, a documented prediction timestamp per feature
Preprocessing state mismatch Scaler, vocabulary, or encoder refit or version-mismatched at serving Package the fitted preprocessing together with the model as a single artifact
Default and missing-value handling A timeout returns zeros at serving, while training had null Explicit missing-value contract and monitoring of the missing rate per feature
Population mismatch Training on exposed or approved cases only, serving on everyone Include exploration traffic; reweight or model the selection process

Detection. Log the served feature vector and prediction for a sample of traffic. Compare per-feature distributions between the logged serving features and the training set, and, more decisively, recompute the features offline for the same entities and timestamps and diff them against the logged values. The diff measures skew directly.

#Feature stores

A feature store is a system that defines features once and serves them for both training and inference.

Component Role
Feature definitions (registry) Named, versioned transformations with ownership and documentation
Offline store Historical feature values (a warehouse-style table), used to build training sets with point-in-time joins
Online store Low-latency key-value lookups of the latest values for serving
Materialization / sync Pipelines that compute features and write them to both stores consistently

What it buys: consistency between training and serving, reuse across teams, and point-in-time correctness. What it costs: an additional system to run, schema and versioning discipline, and freshness limits tied to the materialization schedule. For a small system with a few features, a shared library and logged-feature training data may offer most of the benefit with less machinery.

#Latency and Throughput Levers

Latency is the time for one request; throughput is requests per unit time. Tail latency (p95, p99) is usually the binding constraint because user experience and downstream timeouts are set by the slow requests, not the average.

Lever What it does Tradeoff
Quantization Store weights (and possibly activations) in lower precision, such as 8-bit integers in place of 32-bit floats Smaller memory and faster arithmetic on supporting hardware; some accuracy loss that varies by model and method, so it must be measured on the target task
Pruning / sparsity Remove low-importance weights or structures Speedups depend on hardware and structure; unstructured sparsity often gives memory savings without wall-clock gains
Distillation Train a smaller student to match a larger teacher's outputs (often soft probabilities) A cheaper model with accuracy near the teacher's in many cases; requires a training run and representative data
Caching Store results for repeated inputs or precomputed embeddings Large savings when the request distribution is skewed; adds staleness and invalidation concerns
Batching Group requests so one forward pass serves several Better hardware utilization and throughput; adds queueing delay, so dynamic batching with a maximum wait time balances the two
Model cascade / early exit A cheap model handles easy cases, an expensive one handles the rest Reduces average cost; adds routing logic and a threshold to calibrate
Feature pruning and cheap features Drop costly features with low marginal gain Feature fetches (network calls) often dominate latency more than the model itself
Compiled / optimized runtimes Graph optimization, operator fusion, hardware-specific kernels Engineering effort; behavior can differ slightly from the training framework and should be verified
Horizontal scaling and autoscaling More replicas behind a load balancer Raises throughput, not single-request latency; cold starts and cost
Approximate retrieval Approximate nearest-neighbor search in place of exact Large speedups; recall falls slightly and should be monitored
Interview angle

Before optimizing the model, profile the request: network calls to feature stores, serialization, and preprocessing often account for more of the budget than the forward pass. Then state the lever together with the metric it risks (quantization risks accuracy; batching risks tail latency; caching risks staleness).

Go deeper (optional)

Rough capacity planning: with average per-request service time sss seconds and ccc parallel workers, maximum sustainable throughput is about c/sc/sc/s requests per second. Queueing theory also says that latency rises sharply as utilization approaches 100%, so targets such as 50-70% utilization at peak leave headroom for tails and bursts. These are rules of thumb that depend on the arrival pattern.

#Deployment Strategies

Offline metrics do not guarantee online performance because of skew, feedback effects, and population differences, so rollouts proceed in stages that reveal different problems.

Stage What happens What it catches Limit
Offline validation Holdout metrics, slice metrics, regression tests against a fixed evaluation set, latency benchmarks Obvious quality regressions, resource violations Cannot reveal serving bugs or user response
Shadow mode New model receives live traffic and logs predictions; users see the old model's output Serving errors, latency, skew, distribution of outputs vs the incumbent No user impact measured, and no feedback effects
Canary release New model serves a small slice (for example 1-5%) with automatic health checks Crashes, latency regressions, gross metric drops on real traffic Small slice gives low statistical power for subtle effects
A/B test Randomized split with a pre-registered primary metric, guardrails, and sample size Causal effect on business metrics Needs adequate duration and sample size; interference and novelty effects can bias results
Gradual ramp Increase traffic share in steps while monitoring Scale-dependent issues Slower; needs defined gates between steps
Interleaving (ranking) Mix results from two rankers within one list and attribute clicks High sensitivity for ranking comparisons with fewer users Measures preference, not every business metric
Bandit rollout Adaptively shift traffic toward the better variant Lower cost of exploring a worse arm Harder inference on the final effect size

Rollback. Define the rollback trigger before launch: which metrics, which thresholds, which window. Keep the previous model version deployed and addressable so that rollback is a configuration switch rather than a rebuild. Use feature flags or a routing layer so traffic can be shifted in seconds. When the model's outputs feed stateful consumers (caches, downstream features), rollback may also require invalidating or recomputing those outputs.

Design considerations for A/B tests of ML models: randomize by the right unit (user, rather than request, when experience is persistent); pre-specify guardrails (latency, error rate, fairness slices, revenue); account for multiple comparisons when many metrics are checked; and watch for network or marketplace interference, where treatment and control compete for the same resource, which can bias the measured effect.

#Monitoring

Monitoring needs three layers: system health (latency, errors, throughput, resource use), data quality and drift (inputs and outputs), and model quality (accuracy against outcomes, when available).

#Types of shift

Let xxx be the inputs and yyy the label. The distinctions below define what changed and what monitors can see.

Shift What changes What stays fixed Example Consequence
Covariate shift (data drift) p(x)p(x)p(x) p(y∣x)p(y \mid x)p(y∣x) New user demographic enters the app Model may be extrapolating; accuracy falls where it is out of its training support, and may not fall if the model is correct there
Label shift (prior shift) p(y)p(y)p(y) p(x∣y)p(x \mid y)p(x∣y) Disease prevalence rises during a season Posterior probabilities become miscalibrated; ranking can remain fine; thresholds need adjusting
Concept drift p(y∣x)p(y \mid x)p(y∣x) (anything may change) Fraudsters change tactics; user preferences change The learned mapping is wrong; retraining on fresh labels is needed
Upstream / pipeline change The meaning, units, or availability of a feature Underlying world A source column changes units or starts returning nulls Often abrupt; resembles drift in monitors but is a bug

Drift in p(x)p(x)p(x) is not by itself evidence of lower accuracy, and absence of drift in p(x)p(x)p(x) does not rule out concept drift, because p(y∣x)p(y\mid x)p(y∣x) can change while p(x)p(x)p(x) is stable. Input monitors are early-warning signals that need to be connected to outcomes.

Under label shift, the target prior can be estimated without target labels by solving for new class proportions using the confusion matrix of the existing classifier on held-out data: with confusion matrix CCC (entries P(y^=i,y=j)P(\hat y = i, y = j)P(y^​=i,y=j)) and the model's predicted-label distribution μ\muμ on new data, the new class prior ratio weights solve w=C−1μw = C^{-1}\muw=C−1μ. This assumes label shift holds and CCC is invertible; it is one of the few label-free corrections with a clean derivation.

#Detecting data drift: PSI and KS

Population Stability Index (PSI) compares binned distributions of a feature (or score) between a reference sample and a current sample. With BBB bins, expected (reference) proportions eie_iei​ and actual (current) proportions aia_iai​:

PSI=∑i=1B(ai−ei) ln⁡aiei\mathrm{PSI} = \sum_{i=1}^{B} (a_i - e_i)\,\ln\frac{a_i}{e_i}PSI=i=1∑B​(ai​−ei​)lnei​ai​​

This is the symmetrized KL divergence between the two binned distributions. Common rules of thumb (below about 0.1 small, 0.1 to 0.25 moderate, above 0.25 large) are conventions from credit-scoring practice rather than statistical thresholds.

Kolmogorov-Smirnov (KS) two-sample test uses the maximum gap between the two empirical CDFs, D=sup⁡x∣Fref(x)−Fcur(x)∣D = \sup_x |F_{ref}(x) - F_{cur}(x)|D=supx​∣Fref​(x)−Fcur​(x)∣, for continuous features. It is distribution-free for continuous data.

Issue Why it matters
Sample-size sensitivity With very large samples, KS ppp-values flag tiny, practically irrelevant differences; with small samples, real shifts go undetected. Report effect size (DDD, PSI) alongside any ppp-value
Binning sensitivity (PSI) Results depend on the number and placement of bins; bins are usually set from reference quantiles, and empty bins need smoothing to avoid ln⁡0\ln 0ln0
Univariate only Both examine one feature at a time and miss changes in correlations or joint structure; multivariate options include a domain classifier (train a model to separate reference from current rows; AUC near 0.5 means indistinguishable), or distances on embeddings
Categorical features KS does not apply directly; use PSI, chi-squared, or Jensen-Shannon distance on category frequencies
Multiple testing Monitoring hundreds of features at a 5% level yields many false alarms; correct the thresholds, rank by effect size, or alert on the top features by importance
Seasonality Weekly or annual cycles look like drift if the reference window is mismatched; compare to the same phase of the cycle
Drift is not impact A feature that the model barely uses can drift without consequence; weigh by feature importance or by the change in prediction distribution

Also monitor the model output distribution (score histogram, positive prediction rate), missing-value rate per feature, out-of-range or new-category rate, and schema and freshness of upstream tables. Output and null-rate monitors are cheap, need no labels, and catch many pipeline failures.

#Delayed and missing labels

Ground truth often arrives late (loan default after months), arrives partially, or arrives biased (only reviewed cases are labeled). Options:

Situation Approach
Labels delayed but eventually complete Track metrics on matured cohorts, and report the lag; evaluate on recent cohorts when their labels close
Labels partial or selectively observed Sample a small random audit set for unbiased labels; weight by inverse sampling probability
Labels very slow or absent Use proxy metrics: early engagement signals, user reports, complaint rates, or agreement with a slower, more accurate model
Feedback loops Hold out exploration traffic, since a model that only observes outcomes for items it chose gets a biased picture of the rest

Proxy metrics are useful when they are validated: periodically check the proxy's correlation with the true outcome on matured data, because a proxy can drift away from the quantity it was meant to track.

Interview angle

A well-rounded monitoring answer has three tiers: (1) label-free signals available immediately (input drift, output distribution, null rates, latency), (2) proxy metrics available in hours or days, (3) true performance on matured labels. Then add that alerts are tied to a runbook and an owner, and that thresholds are tuned to limit alert fatigue.

#Slices

Aggregate metrics can mask regressions in subpopulations (region, device, new users, protected groups). Track key metrics per slice, with confidence intervals, since small slices produce noisy estimates.

#Retraining Policies

Policy Trigger Strengths Limits
Scheduled Fixed cadence (daily, weekly, monthly) Simple, predictable May retrain needlessly, or too slowly after sudden change
Triggered Drift or performance alert passes a threshold Responds to need, saves compute Needs well-tuned alerts; labels may lag
Continuous / online learning Update on each event or mini-batch Fast adaptation Risk of instability, poisoning, and feedback loops; harder to audit and reproduce
Manual Human decision Controlled Slow and inconsistent

Choosing cadence: estimate how fast the world changes (the half-life of model accuracy, measured by evaluating older models on newer data), compare against the cost of retraining and the risk each release carries. A common compromise is scheduled retraining with performance-based gates and drift triggers for exceptional events.

Retraining decisions:

  • Window. Training on all history gives more data; a sliding window favors recency. When behavior changes, sample weights that decay with age are a middle path.
  • Warm start vs from scratch. Warm starting is cheaper; retraining from scratch avoids accumulating past quirks and is easier to reproduce.
  • Promotion gate. A retrained model replaces the incumbent only if it passes automated checks: holdout metrics at least as good on recent data and on key slices, calibration within tolerance, latency and size within budget, and no regression on a fixed regression-test set. Then it follows the staged rollout above.
  • Label quality. Retraining on labels generated by the model's own decisions can reinforce its biases; include randomized exploration or independent labels where feasible.

#Model Registry, Versioning, Reproducibility

A model registry is a catalog of trained model artifacts with their metadata and lifecycle stage (for instance: experimental, staging, production, archived).

Item to record Why
Code version (commit hash) and environment (library versions, container image) Reconstruct the training run
Data version / snapshot and query Same data must be recoverable; includes label definitions and time ranges
Feature definitions and preprocessing artifacts Prevent skew; the fitted scaler/encoder is part of the model
Hyperparameters and random seeds Replication and comparison
Evaluation results, including slice metrics and the evaluation dataset version Justify promotion; baseline for future comparison
Lineage (parent model, upstream tables) Impact analysis when a source changes
Approvals and stage transitions Auditability and governance
Serving signature (input schema, output schema) Detect contract violations at inference

Reproducibility caveats: exact bitwise reproduction can fail even with fixed seeds because of nondeterministic GPU kernels, parallel reduction order, and library differences, so the practical target is statistically equivalent results, with seeds and determinism flags used where they are available. Version data as carefully as code, since a model without its data snapshot is not reproducible.

Further practices: automate training as a pipeline (rather than a notebook) so that each run is a tracked, parameterized artifact; keep a fixed golden evaluation set and a small suite of regression tests (known inputs with expected output ranges); and validate input schemas at the serving boundary.

#Failure Modes and Incident Response

Failure mode Typical signal Common root cause First response
Silent feature break Null rate or constant-value spike; score distribution shifts abruptly Upstream schema change, a failed job, unit change Roll back or fall back to defaults; fix the pipeline; backfill
Training-serving skew Offline-online gap from launch; logged vs recomputed features disagree Duplicate feature logic, time-travel in training data Diff logged and recomputed features; unify code paths
Gradual concept drift Slow decay of matured-label metrics Behavior or environment changes Retrain, with updated window and features
Feedback loop Narrowing diversity; self-confirming labels Model decisions determine which labels are seen Add exploration, independent labels, diversity constraints
Latency regression p99 climbs; timeouts Heavier model, slow feature fetch, cold starts, traffic growth Scale out, cache, fall back to a lighter model
Cascading dependency failure Many systems degrade at once An upstream model's change alters this model's inputs Version contracts between models; staged rollouts with downstream checks
Data poisoning / adversarial input Targeted shifts; attacks on thresholds Open data intake, adversaries adapting Rate-limit, validate inputs, monitor for abnormal clusters, review training-data intake
Bad rollout Canary or A/B guardrail breach Insufficient offline coverage Automated rollback to the previous version

Incident process, in rough order: detect (alert or user report), triage severity and blast radius, mitigate first (roll back, switch to a fallback model or rule-based default, disable the feature), diagnose root cause with logged inputs and versions, fix and validate, then run a blameless post-mortem that produces concrete follow-ups (a new monitor, a new test, a clearer data contract). Prefer mitigation over diagnosis during the incident, since restoring service limits harm while the investigation continues.

Fallbacks and graceful degradation should exist before they are needed: a simpler model, cached last-known-good predictions, or a rules-based default when the model service times out or the inputs fail validation. The fallback behavior itself should be tested and monitored.

Warning

Alerts that fire too often get ignored, and alerts that never fire hide real failures. Treat thresholds as hypotheses: review them after incidents, and attach each one to an owner and a runbook.

#Responsible-AI Basics

Operational ML comes with obligations around fairness, privacy, and transparency. The material below is the minimal toolkit usually expected in design discussions.

#Fairness metrics at a glance

Let Y^\hat YY^ be the decision, YYY the true outcome, and AAA a protected attribute (group). The common group criteria are:

Criterion Condition Intuition
Demographic (statistical) parity P(Y^=1∣A=a)P(\hat Y=1 \mid A=a)P(Y^=1∣A=a) equal across groups Same positive rate per group, regardless of outcome base rates
Equal opportunity P(Y^=1∣Y=1,A=a)P(\hat Y=1 \mid Y=1, A=a)P(Y^=1∣Y=1,A=a) equal (equal true positive rates) Qualified people are accepted at equal rates
Equalized odds Equal true positive and false positive rates across groups Error rates match across groups
Predictive parity P(Y=1∣Y^=1,A=a)P(Y=1 \mid \hat Y=1, A=a)P(Y=1∣Y^=1,A=a) equal (equal precision) A positive decision means the same thing for each group
Calibration within groups P(Y=1∣score=s,A=a)P(Y=1 \mid \text{score}=s, A=a)P(Y=1∣score=s,A=a) equal for each sss Scores carry the same probabilistic meaning in each group

These criteria generally cannot all hold at once. When group base rates P(Y=1∣A=a)P(Y=1\mid A=a)P(Y=1∣A=a) differ and the classifier is imperfect, calibration within groups and equal false positive and false negative rates are mutually incompatible, apart from degenerate cases. Choosing a criterion is therefore a policy decision tied to the harm of each error type, to be made with stakeholders and documented.

Practical points: compute metrics per group with confidence intervals; examine whether protected attributes are available at evaluation time (they may be excluded from the model but still needed for auditing); note that dropping the protected feature does not remove its influence when proxies (zip code, name patterns) are present; and consider mitigation at three stages: pre-processing (reweighting, data repair), in-training (constraints or penalties), or post-processing (group-specific thresholds), each with its own accuracy-fairness tradeoff and legal considerations that depend on jurisdiction.

#Privacy

Concept Key point
Data minimization and retention limits Collect and keep only what the task needs; delete on schedule
PII handling Pseudonymize or tokenize identifiers; restrict access; avoid placing raw identifiers in feature stores and logs
Anonymization limits Removing direct identifiers does not guarantee anonymity, since combinations of quasi-identifiers can re-identify individuals (the motivation for k-anonymity and its extensions)
Model leakage Models can memorize training examples; membership inference and extraction attacks exploit this, with risk higher for overfit models and rare records
Differential privacy A formal guarantee: a mechanism MMM is (ε,δ)(\varepsilon,\delta)(ε,δ)-DP if for datasets differing in one individual, P(M(D)∈S)≤eεP(M(D′)∈S)+δP(M(D)\in S) \le e^{\varepsilon}P(M(D')\in S)+\deltaP(M(D)∈S)≤eεP(M(D′)∈S)+δ. Training with DP-SGD (per-example gradient clipping plus noise) provides it, at a cost in accuracy that grows as ε\varepsilonε shrinks
Federated learning Training happens on-device and only updates are shared; this reduces raw data movement but does not by itself guarantee privacy, as updates can leak information without additional protections

Also in scope: transparency (model cards and datasheets that record intended use, data, metrics by slice, and limits), explainability suited to the audience, human oversight for high-stakes decisions, and monitoring for harm after launch, because fairness and privacy properties can degrade as the data drifts.

Interview angle

When asked about fairness, name at least two criteria, state that they conflict when base rates differ, and tie the choice to the cost of each error type in the application. That demonstrates that a metric choice is a product decision with tradeoffs, in addition to a formula.

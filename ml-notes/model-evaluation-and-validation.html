Model Evaluation & Validation

Building a model is half the job; knowing whether it’s any good is the other half, and it’s where most candidates are thinnest. This chapter is about measuring honestly. We start from the confusion matrix that every classification metric is built on, untangle precision from recall and the threshold that trades them, separate ROC-AUC from PR-AUC, cover calibration and ranking metrics, then turn to regression metrics and — crucially — how to split data so your estimate isn’t a lie. The recurring theme: the metric is a modeling decision, and choosing the wrong one is how good models get shipped to do the wrong thing.

What you'll be able to say after this chapter
  • Read a confusion matrix and derive precision, recall, and F1 from it cold.
  • Explain the precision–recall tradeoff and how the threshold moves it.
  • Say exactly when PR-AUC beats ROC-AUC (hint: heavy imbalance).
  • Define calibration and why a well-ranked model can still be dishonest.
  • Choose a cross-validation scheme that respects time and groups — no leakage.

#The Confusion Matrix

Every classification metric is an arithmetic combination of four counts, so the confusion matrix is the foundation you build everything else on. For a binary problem it cross-tabulates what actually happened against what the model predicted.

Four cells, and every classification metric is just a ratio of them.

Predicted Positive Predicted Negative
Actually Positive True Positive (TP) False Negative (FN) — a miss
Actually Negative False Positive (FP) — a false alarm True Negative (TN)

The two error types are not interchangeable, and naming them correctly matters. A False Positive (Type I error) is a false alarm — you flagged something that was fine. A False Negative (Type II error) is a miss — you let something real slip through. Which one hurts more is entirely domain-dependent, and that asymmetry is what drives every metric choice in this chapter.

Memory hook

False Positive = “crying wolf” (Type I). False Negative = “missing the wolf” (Type II). Spam filter: a False Positive eats your real email; a False Negative just lets spam through — so you tune toward avoiding False Positives. Cancer screen: a False Negative is deadly — so you tune toward avoiding those. The cost asymmetry picks the metric.

Interview angle

Always ask, or state, which error is worse here. Candidates who optimize a model without distinguishing the cost of a miss from the cost of a false alarm signal they’ve never shipped anything. Tie it to the business: “in fraud, a missed fraud costs us the transaction; a false alarm costs a customer’s goodwill — those aren’t equal.”

#Classification Metrics

From those four cells come the metrics you’ll quote constantly. The danger metric is accuracy — (TP+TN)/total — because it collapses under imbalance: on a dataset that’s 99% negative, “always predict negative” scores 99% and is worthless. Precision and recall are the honest pair.

Metric Formula Reads as Use when
Accuracy TP+TNall\frac{TP+TN}{\text{all}}allTP+TN​ Overall correctness Classes are balanced
Precision TPTP+FP\frac{TP}{TP+FP}TP+FPTP​ Of those I flagged, how many were right? False alarms are costly
Recall (TPR) TPTP+FN\frac{TP}{TP+FN}TP+FNTP​ Of the real positives, how many did I catch? Misses are costly
F1 2PRP+R\frac{2PR}{P+R}P+R2PR​ Harmonic mean of P and R Imbalance, want one number
Specificity (TNR) TNTN+FP\frac{TN}{TN+FP}TN+FPTN​ Of the real negatives, how many did I clear? Care about the negative class

Precision answers “when I say positive, am I right?” — it’s hurt by false alarms. Recall answers “did I find all the positives?” — it’s hurt by misses. F1 is their harmonic mean, not the arithmetic mean, deliberately: the harmonic mean stays low unless both are high, so a model can’t game F1 by maxing one and tanking the other.

Memory hook

Precision = “of my alarms, how many were real?” Recall = “of the real ones, how many did I sound an alarm for?” Precision polices false alarms; recall polices misses. F1 is the harmonic mean — it refuses to be fooled by one good number.

Interview angle

Expect “precision or recall for X?” Cancer screening → recall (never miss a case; false alarms get a follow-up test). Spam → precision (never trash a real email). Search results → precision (the top results must be relevant). Say the cost of each error type out loud and the answer falls out.

#Threshold: Precision vs Recall

Here’s the idea that ties the last section together: most classifiers output a probability, and you turn it into a label by picking a threshold (default 0.5, but that’s just a default). Precision and recall are not fixed properties of the model — they move as you slide the threshold, and they move in opposite directions.

Slide the threshold high for precision, low for recall — you can’t max both at once.

Raise the threshold and you only flag the cases you’re most sure about: precision climbs, recall falls (you miss the borderline positives). Lower it and you flag aggressively: recall climbs, precision falls (more false alarms). This is the precision–recall tradeoff, and the right threshold is a business decision, not a default — set it by the relative cost of a miss versus a false alarm.

Memory hook

The threshold is a dial, not a constant. Crank it up → cautious → high precision, low recall. Crank it down → trigger-happy → high recall, low precision. 0.5 is a default, not a law — set it by what an error costs.

Interview angle

“Your model’s recall is too low — what do you do?” First, cheap: lower the threshold (no retraining needed) and accept the precision hit. Then: resample/reweight for imbalance, add features, or change the model. Reaching for “lower the threshold” first shows you understand that precision and recall are threshold-dependent, not intrinsic.

#ROC-AUC vs PR-AUC

To judge a model across all thresholds at once, you use an area-under-curve summary. There are two, and knowing when each one lies is a classic senior question.

The ROC curve plots True Positive Rate (recall) against False Positive Rate as the threshold sweeps. ROC-AUC is the area under it, interpretable as the probability the model ranks a random positive above a random negative. 0.5 is random, 1.0 is perfect. The PR curve plots Precision against Recall over the same sweep, and PR-AUC is its area.

ROC can look great on imbalanced data; PR tells the truth because precision feels the flood of negatives.

ROC-AUC PR-AUC
Axes TPR vs FPR Precision vs Recall
Baseline (random) 0.5 always The positive class prevalence
Sensitive to imbalance? No — can look misleadingly good Yes — reflects rare-class difficulty
Use when Classes roughly balanced; care about both classes Positive class is rare and is what you care about

The key insight: FPR has the huge negative count in its denominator, so on imbalanced data a flood of false positives barely moves it — ROC-AUC stays optimistically high. Precision has the false positives in its denominator without the true negatives, so it feels every false alarm. When positives are rare and they’re what you care about (fraud, disease, click prediction), PR-AUC is the honest summary.

Memory hook

On a needle-in-a-haystack problem, ROC-AUC flatters and PR-AUC tells the truth. ROC dilutes false positives in a sea of true negatives; precision doesn’t get to hide them. Rare positive class → trust PR-AUC.

Interview angle

“You have 1% fraud and ROC-AUC is 0.95 — are you happy?” The trap is yes. Strong answer: ROC-AUC is inflated by the 99% negatives; check PR-AUC and the precision/recall at your operating threshold before celebrating. This single distinction is one of the most reliable senior-vs-junior separators in evaluation.

#Calibration

Ranking well and being honest about probabilities are different things, and the gap is calibration. A model is calibrated if, among all the times it says “0.7,” the event really happens about 70% of the time. AUC only cares about order; calibration cares about whether the number means what it says.

A calibrated model’s confidence matches reality; the diagonal is perfect.

This matters whenever you act on the probability itself — expected-value decisions, pricing, risk thresholds, or feeding the score into downstream math. A model can have great AUC and terrible calibration: it ranks cases correctly but is systematically over- or under-confident. You diagnose it with a reliability diagram (predicted probability vs observed frequency) and fix it on held-out data with Platt scaling (fit a sigmoid) or isotonic regression (a flexible monotonic fit).

Model Calibration out of the box Note
Logistic regression Usually good Trained on log-loss; can drift if heavily regularized, reweighted or misspecified
Naive Bayes Poor Independence assumption pushes probs to 0/1
SVM Uncalibrated scores (no probabilities) Needs Platt scaling
Deep nets / boosted trees Deep nets: often overconfident; boosted trees/RF: often distorted (sigmoid-shaped, underconfident) Check a reliability diagram; calibrate if you act on the number
Memory hook

Calibration is honesty, not accuracy. “When I say 70%, does it happen 70% of the time?” AUC grades the ranking; calibration grades the number. A model can ace one and flunk the other.

Go deeper (optional)

Don’t conflate calibration with discrimination (AUC). You can have perfect ranking and awful calibration (just squash all scores toward 0.5) or perfect calibration and poor ranking. If you only need to threshold or rank, calibration may not matter; if you multiply the probability into a decision, it’s essential.

#Ranking Metrics: NDCG vs MAP vs MRR

When the output is an ordered list — search, recommendations, retrieval — accuracy and AUC miss the point: what matters is whether the good items are near the top. Three metrics dominate, differing in what they reward.

Metric Rewards Use when
MRR (Mean Reciprocal Rank) The rank of the first relevant item One right answer (Q&A, “I’m feeling lucky”)
MAP (Mean Average Precision) Precision across all relevant items, binary relevance Multiple relevant items, relevant-or-not
NDCG (Normalized Discounted Cumulative Gain) Graded relevance, discounted by position Items have degrees of relevance (star ratings)

All three share the position-discount instinct: a relevant result at rank 1 is worth more than the same result at rank 10. NDCG is the most general because it handles graded relevance (a 5-star match beats a 3-star match) and normalizes against the ideal ordering, so scores are comparable across queries. MRR is the simplest — just 1/(rank of the first hit) — and fits “single correct answer” tasks.

Memory hook

MRR cares only about the first good hit. MAP cares about all the good hits, present-or-absent. NDCG cares about all of them and how good each is, discounted by position. Increasing sophistication: first → all → all-and-graded.

Interview angle

“How would you evaluate a recommender?” Don’t say accuracy. Say a ranking metric and justify it: NDCG if you have graded feedback (ratings, watch time), MAP for binary relevance with several right answers, MRR if there’s essentially one. Then mention that offline ranking metrics are a proxy — the real test is an online A/B on engagement (see ML System Design Interview Prep).

#Regression Metrics

For continuous targets the question shifts to how far off, on average, and the choice among metrics is mostly about how you want to treat large errors and whether you want a unit-free score.

Metric Behavior Use when
MAE Mean absolute error; robust to outliers Outliers shouldn’t dominate; want error in original units
MSE Mean squared error; punishes large errors hard Big misses are especially bad
RMSE √MSE; same units as the target, still outlier-sensitive Want MSE’s penalty but readable units
R² Fraction of variance explained (1 = perfect, 0 = mean-baseline) Want a unit-free “how much better than guessing the mean”

The core tradeoff is MAE vs MSE/RMSE: squaring makes MSE punish big errors disproportionately, so it’s the right choice when a single large miss is unacceptable — but that same squaring makes it sensitive to outliers, which MAE shrugs off. R² rescales error against a “predict the mean” baseline, giving a unit-free score, but it can be misleadingly high on a strong trend and even go negative when the model is worse than the mean. (Adjusted R2R^2R2, which penalizes adding useless features, is covered in Regression Methods.)

Memory hook

MAE treats all errors fairly (robust). MSE/RMSE square the error, so it obsesses over the big misses (outlier-sensitive). R² answers “how much better than just guessing the average?” — unit-free, but can flatter you.

Interview angle

“MAE or RMSE?” Answer with the outlier story: RMSE if large errors are disproportionately costly and the data is clean; MAE if outliers exist and you don’t want a few of them to dictate the model. If asked why a model has R² of 0.0 — it’s no better than predicting the mean; negative R² means worse than the mean.

#Cross-Validation: How to Split Data

A single train/test split gives a noisy estimate — you got lucky or unlucky with which points landed in test. Cross-validation averages over several splits for a stabler estimate, but the way you split must respect the structure of your data, or you leak the future into the past and your metric becomes a fantasy.

k-fold rotates the test fold; but time and groups demand special splits.

Scheme How it works Use when
k-fold Split into k folds; each takes a turn as test Standard i.i.d. tabular data
Stratified k-fold k-fold preserving class proportions in each fold Classification, especially imbalanced
Leave-One-Out k = n; each point is its own test fold Tiny datasets (expensive)
Time-series split Always train on past, test on future Temporal data — never shuffle
Group k-fold Keep each entity entirely in one fold Repeated users/patients/docs

The two splits that prevent leakage are the ones interviewers probe. Time-series CV never shuffles — you train on the past and test on the future, because random shuffling would let the model “see tomorrow” to predict today. Group CV keeps all rows of one entity (a patient, a user) together, so the model can’t memorize an individual in training and get credit for “predicting” them in test. And the golden rule from Fundamentals still binds: fit every preprocessing step (scaling, imputation) inside the training fold only, then apply it to the validation fold.

Memory hook

k-fold for ordinary data. Stratify when classes are imbalanced. Split by time for time series (never peek at the future). Split by group when the same entity repeats (never let it sit on both sides). The wrong split = silent leakage = a beautiful, lying score.

Interview angle

“How would you cross-validate a model that predicts next month’s sales?” The trap is plain k-fold. Right answer: a time-based split — train on earlier periods, validate on later ones, never shuffle — because shuffling leaks future information and inflates the score. Mention that preprocessing stats must be fit on the training fold only.

#Which Metric When

The chapter in one table — match the metric to the problem, because the metric is the objective you’re really optimizing.

Problem Metric
Balanced classification Accuracy (or AUC)
Imbalanced classification PR-AUC, F1, precision/recall at threshold
Cost of a miss ≫ false alarm Optimize recall
Cost of a false alarm ≫ miss Optimize precision
Acting on the probability value Calibration (reliability diagram + Platt/isotonic)
Ranking / search / recommendation NDCG, MAP, or MRR
Regression, clean data, punish big errors RMSE
Regression with outliers MAE
“How much better than the mean?” R²

The closing principle ties the chapter to Fundamentals: separate the offline ML metric (what you compute on held-out data) from the online business metric (what you A/B test in production). A model that wins on offline AUC can still lose on revenue or engagement — so the metric you optimize must be a faithful proxy for the value you actually care about.

Interview angle

The unifying senior insight: choosing the metric is a modeling decision, made before you train. For any “how would you evaluate X?” answer in two layers — the offline metric tied to the error costs, and the online metric (A/B test on the business outcome) that’s the real arbiter. Saying “I’d pick the metric from what an error costs the business” is the line that lands.

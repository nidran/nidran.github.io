LLM Evaluation

Offline scores are cheap lies unless you know what they measure and what they miss.

Language models do not output a single correct label; they output open-ended text under prompts you chose, decoded with knobs that inject randomness. LLM evaluation is the discipline of turning that mess into decisions: ship or hold, model A or B, safe enough for this surface. The interview version is not reciting benchmark names—it is naming a hierarchy of evals (cheap regression → benchmarks → judges → humans → online experiments), picking metrics that match the failure mode, and reporting uncertainty so a 0.5-point leaderboard twitch does not fool anyone.

What you'll be able to say after this chapter
  • Explain why n-gram scores, perplexity, and static benchmarks each break for instruction-tuned chat models.
  • Design a versioned golden set from production logs without contaminating training or the test pool.
  • Compute pass@k with the unbiased estimator and defend execution-based code eval.
  • Run LLM-as-judge with rubrics, bias probes, and human agreement metrics (κ, Spearman, win-rate/Elo).
  • Split RAG and agent evals into component vs end-to-end, with links to retrieval metrics and faithfulness.
  • Size an offline comparison: confidence intervals on accuracy and ~1,200 paired items for a 2-point lift under McNemar.
  • Close with online guardrails and point to A/B Testing & Online Experimentation for causal launch decisions.

#Why LLM evaluation is hard

Classical model evaluation assumes a fixed label space and a loss you can average. LLMs violate every convenience:

Difficulty What breaks Practical consequence
Open-ended outputs Many strings are equally good Reference metrics need gold answers or rubrics
Multiple valid answers Paraphrase, style, language Exact match punishes correct but differently worded replies
Non-determinism Sampling (temperature, top-ppp) Same prompt → different scores unless you fix the seed or use greedy decode
Prompt sensitivity Small wording changes swing quality You must version prompts with datasets ([[decoding-strategies
Distribution shift Prod queries ≠ academic benchmarks High MMLU, low user satisfaction

Evaluation is therefore not one number—it is a stack of complementary checks, each trading cost, coverage, and fidelity.

flowchart TB
  U[Unit tests / regression suite] --> B[Offline benchmarks]
  B --> J[LLM-as-judge]
  J --> H[Human evaluation]
  H --> O[Online A/B & guardrails]

Unit tests / regression suites are tiny, hand-written cases you run on every merge: JSON schema, citation format, refusal on a known jailbreak, “don’t call tool X without user confirm.” They are the CI of LLM products—fast, brittle if neglected, invaluable for catching regressions.

Offline benchmarks (MMLU, HumanEval, etc.) give broad coverage cheaply but saturate and leak (see below).

LLM-as-judge scales subjective quality when humans are too slow—at the cost of judge biases you must measure.

Human eval remains the reference for preference alignment (RLHF vs DPO, LLM Training & Alignment).

Online A/B measures what users and revenue actually do—see A/B Testing & Online Experimentation.

Memory hook

Cheap tests catch regressions; benchmarks catch breadth; judges catch nuance; humans catch truth; A/B catches reality.

Interview angle

Weak: “We’d look at perplexity and BLEU.” Strong: regression suite on every deploy, task-specific golden set with versioning, LLM-judge with position-bias controls, human spot-check on disagreements, powered online test on downstream metric with safety/latency guardrails.

Rapid fire — Why & hierarchy

Open outputs, many valid answers, sampling noise, prompt sensitivity. Eval stack: unit/regression → benchmarks → LLM judge → human → online A/B. No single metric is sufficient. Version prompts with datasets. Prod ≠ benchmark distribution.

#Building an evaluation set

Metrics are only as honest as the items you score.

#Golden sets and production mining

A golden set is a frozen collection of (prompt, optional context, reference or rubric) with expected behavior. Sources:

  • Hand-authored — edge cases you know users hit (pricing policy, medical disclaimer).
  • Production logs — sample real queries; stratify by intent, difficulty, language, and failure tags from support tickets.
  • Adversarial buckets — jailbreaks, injection attempts, trick questions with known wrong answers.

Turn logs into labels with human annotators or SME review; never auto-label with the model you are shipping.

#Stratification and difficulty

Report metrics per slice (easy/medium/hard, domain, tool-use vs chit-chat). Aggregate accuracy hides “great on head traffic, catastrophic on refunds.” Use explicit difficulty tags or model-based pre-labeling, then human audit of the hard bucket.

#Versioning and contamination

Treat prompt template, model checkpoint, judge model, and dataset version as a single artifact. When you fine-tune or distill, scrub training data for benchmark leakage and near-duplicates of your golden set (data leakage). Holding out a “private” eval that never touches training is the same golden rule as Fundamentals: test once, honestly.

Contamination

Public benchmarks appear in pretraining corpora. Leaderboard gains may be memorization, not capability. Prefer held-in-house sets and periodic refresh from fresh prod traffic.

Go deeper (optional)

For RAG, golden sets need retrieved contexts frozen per question—otherwise you are evaluating generation and retrieval drift in one number. See Retrieval-Augmented Generation (RAG).

#Reference-based text metrics

When you have a reference answer, overlap metrics are cheap baselines. They correlate with humans on narrow tasks (short QA, extraction) and fail on creative or long-form generation.

Metric What it measures When it works When it lies
Exact match (EM) Normalized string equality Single-span answers (e.g. SQuAD-style) Any paraphrase fails
Token F1 Token overlap precision/recall vs gold QA with flexible phrasing Synonyms, word order, extra explanation
BLEU Weighted n-gram precision vs reference; brevity penalty punishes short outputs MT with close references Rewards generic fluent text; poor on dialogue
ROUGE-N N-gram recall vs reference Summarization (cover reference phrases) Ignores coherence and factuality
ROUGE-L Longest common subsequence F1 Summary ordering Same factuality blind spot
chrF Character n-gram F-score Morphologically rich languages Still reference-dependent
BERTScore Cosine similarity of contextual embeddings (per token, matched) Paraphrase-tolerant QA Can score fluent wrong facts highly
Interview angle

If asked “BLEU vs ROUGE”: BLEU emphasizes precision (did you copy reference n-grams?); ROUGE emphasizes recall (did you cover reference content?). Neither checks truth—pair with execution, retrieval faithfulness, or human/LLM rubrics for hallucination.

Detokenize before scoring (tokenization); otherwise token F1 is not comparable across models.

Rapid fire — Reference metrics

EM/F1 for short QA spans. BLEU = n-gram precision + brevity penalty (MT). ROUGE-N/L = n-gram/LCS recall (summaries). chrF = character F1. BERTScore = embedding similarity—better paraphrase, not better facts. All need gold references; weak on open-ended chat.

#Code and math evaluation

#pass@k and the unbiased estimator

For code, draw nnn completions per problem; the problem is solved if any of the first kkk passes unit tests. If ccc of nnn samples pass, the unbiased pass@k estimator (when n≥kn \ge kn≥k) is:

pass@k=1−(n−ck)(nk)\text{pass@k} = 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}pass@k=1−(kn​)(kn−c​)​

Worked example: n=20n=20n=20 independent samples, c=5c=5c=5 pass tests, k=1k=1k=1:

pass@1=1−(151)(201)=1−1520=0.25\text{pass@1} = 1 - \frac{\binom{15}{1}}{\binom{20}{1}} = 1 - \frac{15}{20} = 0.25pass@1=1−(120​)(115​)​=1−2015​=0.25

For n=100n=100n=100, c=30c=30c=30, k=10k=10k=10: pass@10≈0.977\text{pass@10} \approx 0.977pass@10≈0.977—most problems are solved if at least one of ten tries can succeed when 30% of single draws pass.

HumanEval and MBPP report pass@1 with n≥200n \ge 200n≥200 for stable estimates on hard tasks.

#Execution sandboxes and extraction

  • Run tests in an isolated sandbox (no network, time/memory caps)—latency and security are part of eval design (LLM Inference).
  • Answer extraction matters: models wrap code in markdown or prose; brittle parsers create format sensitivity—measure with and without a canonical extractor.
  • Math: sympy/numeric checks, or LLM graders on equivalence classes; beware LaTeX formatting games.
Memory hook

pass@k answers: “If my user gets kkk tries, what fraction of tasks succeed at least once?”

#Perplexity

Perplexity is exp⁡(Hˉ)\exp(\bar{H})exp(Hˉ) where Hˉ\bar{H}Hˉ is average token negative log-likelihood on a corpus—equivalently, the perplexity of a held-out text under the model (cross-entropy loss):

PPL=exp⁡(−1T∑t=1Tlog⁡p(xt∣x<t))\text{PPL} = \exp\left(-\frac{1}{T}\sum_{t=1}^{T}\log p(x_t \mid x_{<t})\right)PPL=exp(−T1​t=1∑T​logp(xt​∣x<t​))

Lower perplexity means the model assigns higher probability to the actual next tokens—fluency under the training distribution.

Do not compare perplexity across tokenizers—different BPE merges change TTT and the partition of probability mass (Tokenization).

After instruction tuning, perplexity on web text poorly tracks helpfulness, safety, or factuality; use task evals instead. Perplexity remains useful for pretraining comparisons on the same tokenizer/vocab and for catching catastrophic corruption after quantization.

Rapid fire — PPL

PPL = exp(average token CE). Lower = better fit to eval text. Same tokenizer/vocab only. Weak proxy for chat quality post-alignment. Good for pretrain/quant sanity checks.

#LLM-as-judge

When references are missing or subjective, a stronger model (or ensemble) scores outputs against a rubric.

#Modes

Mode How Pros Cons
Pointwise Rate one response 1–5 on dimensions Simple aggregation Absolute scores drift
Pairwise Which of A or B is better? Stable for preferences Needs two samples
Reference-guided Score against gold / retrieved context Grounds factuality Needs references

Design rubrics with observable criteria (“ cites source,” “arithmetic correct,” “refuses policy violation”) not vague “quality.” Chain-of-thought judging (judge reasons before score) often improves consistency—hide reasoning from the user-facing model.

#Known biases and mitigations

Bias Symptom Mitigation
Position First answer wins in pairwise Swap order, average; reject inconsistent judges
Verbosity Longer = better Rubric cap on length; length-normalized pairwise; strip preambles
Self-preference Judge favors own family Use third-party judge; blend judges; calibrate on gold
Anchoring Early dimension skews later Separate calls per dimension or blind ordering

Measure bias with position tests (same pair, swapped), length-matched pairs, and known-answer probes (one response clearly wrong).

#Agreement with humans

  • Cohen's κ for categorical ratings (chance-corrected agreement).
  • Spearman / Kendall for rankings across models vs human panels.
  • Win rates and Bradley–Terry / Elo from pairwise outcomes—Chatbot Arena style: update Δrating\Delta\text{rating}Δrating from expected vs actual wins.

Disagreements flag items for human adjudication—do not silently average conflicting judges.

Interview angle

Strong judges answer: which mode (pairwise for prefs), rubric dimensions, swap-order protocol, third-party judge to fight self-preference, κ vs human on a 200-item anchor set, escalate ties to humans.

Rapid fire — Judges

Pointwise / pairwise / reference-guided. Concrete rubrics + optional CoT. Position → swap & average. Verbosity → length controls. Self-preference → external judge mix. Validate with κ, Spearman, win rates, Elo. Disagreements → human.

#Meta-evaluation of judges

Treat the judge as a model with its own QA bar:

  • Test–retest reliability — same item, same rubric, multiple draws; unstable judges get temperature cuts or structured JSON outputs.
  • Inter-judge agreement — multiple LLM or human judges; low agreement surfaces hard items for adjudication.
  • Adversarial probes — pairs where one response is clearly worse (injected factual error); judges should not tie.
  • Stratified analysis — accuracy of the judge by difficulty, domain, and failure type, mirroring how you slice model metrics.

#Human evaluation

Humans remain the anchor when stakes are high or labels are subjective:

  • Side-by-side preference — show two completions; pick better (foundation of RLHF preference data).
  • Likert ratings — helpfulness, accuracy, tone on 1–5; use clear anchors (“3 = acceptable, not delightful”).
  • Domain expert review — lawyers, clinicians, finance SMEs judge real workflows, not toy prompts.
  • Red teaming — adversarial sessions probing safety (overlaps with safety evals below).

Sample enough items per slice for powered comparisons; blind models when possible to avoid brand bias.

Rapid fire — Human & meta-eval

Side-by-side for prefs; Likert with anchored rubrics; SMEs for domain truth. Judge QA: test–retest, inter-judge agreement, adversarial probes, stratified breakdown. Blinding reduces brand bias.

#RAG and agent evaluation

#RAG: component vs end-to-end

RAG fails in two places—retrieval and generation—so split metrics:

Layer What to measure Typical metrics
Retriever Did relevant evidence appear in top-kkk? Recall@kkk, MRR, NDCG ([[ranking-metrics
Generator Faithful to context? On-topic? Faithfulness / groundedness, answer relevance, context precision/recall
End-to-end User question answered correctly Human or rubric on final output; cite entity match

Faithfulness catches intrinsic hallucination (answer contradicts or adds beyond context); answer relevance catches answers that quote docs but ignore the question. Link generation faithfulness to Hallucination mitigation.

#Agents: trajectory vs outcome

Agents call tools over multiple steps (Transformers & Attention for long contexts, LLM Inference for latency budgets):

  • Task success — did the user goal complete (ticket filed, chart rendered)?
  • Tool-call validity — right tool, schema-valid args, no hallucinated APIs.
  • Planning quality — sensible decomposition vs circular re-planning; often judged in trajectory eval.
  • Trajectory eval — score each step (plan quality, recovery after error) vs outcome-only (cheap but misses unsafe paths).
  • Step efficiency — solved in 3 steps vs 15 affects cost and user patience.
  • Budgets — cap latency, token cost, and tool side effects as first-class metrics alongside success rate.

Failure mode categorization — track rates for hallucination, retrieval miss, planning failure, tool misuse, policy violation—not one aggregate accuracy.

Failure mode dashboards feed the next golden-set slice and regression tests.

Rapid fire — RAG & agents

Split retrieval (recall/MRR/NDCG) from generation (faithfulness, relevance). End-to-end for product truth. Agents: success, valid tools, trajectory vs outcome, step count, cost/latency guardrails.

#Safety evaluation

Safety is not binary “refuse all”—over-refusal breaks product (refusing benign medical FAQs) while under-refusal risks harm.

  • Red teaming — adversarial personas, multi-turn escalation, automated attack generators.
  • Jailbreak / prompt-injection suites — static transcripts plus dynamic tests with untrusted retrieved content (RAG injection).
  • Toxicity / bias — slice by demographic descriptors; measure rates and severity, not single scalar “toxicity score.”
  • Refusal quality — correct refusals on policy violations; false refusal rate on in-scope help requests.

Log incidents in prod as new regression cases. Pair offline suites with guardrail metrics online (reports per 1k sessions, escalation rate).

Over-refusal

Optimizing refusal rate alone teaches models to say “I can’t help” everywhere. Report conditional accuracy: helpfulness given safe queries, refusal given unsafe.

#Benchmark literacy (and skepticism)

Know the headline benchmarks—and why leaders distrust them alone:

Benchmark What it tests Caveat
MMLU Multi-subject multiple-choice knowledge Saturating; contamination sensitive
HellaSwag Commonsense sentence completion Format hacks; less chat-relevant
ARC (Easy/Challenge) Grade-school science MC Narrow reasoning style
GSM8K Math word problems Parser/format sensitivity
HumanEval / MBPP Code synthesis pass@k depends on nnn; sandbox discipline
MT-Bench Multi-turn dialogue LLM-judge heavy; domain drift

Static benchmarks saturate as models train on similar data; leaderboard overfitting chases points without user value. HELM-style reporting—many scenarios, metrics, and calibration slices—is the antidote: report accuracy, robustness, fairness, efficiency together, not one heroic number.

Refresh public-facing numbers with private holdouts and prod-sampled evals.

Rapid fire — Benchmarks

MMLU/ARC/HellaSwag = knowledge/commonsense MC. GSM8K = math. HumanEval/MBPP = code (pass@k). MT-Bench = multi-turn chat. Saturate + leak → trust in-house refresh + multi-metric HELM mindset.

#Statistics of evaluation

A finite eval set gives a sample of accuracy p^\hat{p}p^​; treat uncertainty explicitly (p-values & statistical power, Calibration for probability quality elsewhere).

#Confidence intervals on accuracy

If kkk of nnn items are correct, Wilson score 95% CI is tighter than naive p^±1.96p^(1−p^)/n\hat{p} \pm 1.96\sqrt{\hat{p}(1-\hat{p})/n}p^​±1.96p^​(1−p^​)/n​. Example: 850/1000850/1000850/1000 correct → p^=0.85\hat{p}=0.85p^​=0.85, Wilson interval approximately [0.827,0.871][0.827, 0.871][0.827,0.871]—about ±2.2\pm 2.2±2.2 points at n=1000n=1000n=1000.

Bootstrap resampling of items also works when metrics are non-smooth (e.g. custom rubric scores).

#Paired comparison on the same items

Compare models A and B on identical prompts—use McNemar on discordant pairs (B right/A wrong vs A right/B wrong), not two independent proportion tests.

Worked sizing: Suppose A is 85% accurate, B is 87% on the same nnn items, with 4% “only B correct” and 2% “only A correct” (discordant rates). For two-sided α=0.05\alpha=0.05α=0.05, 80% power:

n≈(zα/2+zβ)2(p01+p10)(p10−p01)2≈(1.96+0.84)2⋅0.060.022≈1,176n \approx \frac{(z_{\alpha/2}+z_{\beta})^2 (p_{01}+p_{10})}{(p_{10}-p_{01})^2} \approx \frac{(1.96+0.84)^2 \cdot 0.06}{0.02^2} \approx 1{,}176n≈(p10​−p01​)2(zα/2​+zβ​)2(p01​+p10​)​≈0.022(1.96+0.84)2⋅0.06​≈1,176

You need on the order of 1,200 labeled examples to reliably detect a 2 percentage point paired accuracy lift under those discordant rates. (If you evaluated arms on independent random halves of traffic, required nnn per arm is far larger—roughly 4,700+ per model for similar gaps—another reason paired item design wins offline.)

#Variance from sampling

With T>0T>0T>0, rerun stochastic evals with fixed seeds or report mean ± std over RRR samples. For regression suites, prefer greedy decode (T=0T=0T=0) for determinism unless the product is explicitly stochastic.

Interview angle

When someone cites “85.3% vs 85.1%”: ask nnn, paired or not, CI width, and whether prompts matched. Reject point deltas smaller than the Wilson half-width.

#Online evaluation

Offline wins do not guarantee prod wins—latency, UX, and user adaptation matter. Complement offline stacks with:

Signal What it tells you
Thumbs up/down, regenerations Implicit preference; biased by UI placement
Edits / copy rate User fixes model output—strong quality signal
Downstream KPIs Conversion, resolution time, ticket reopen rate
A/B tests Causal lift on primary metric—design in [[ab-testing-and-experimentation
Guardrails Latency p99, cost per session, safety incidents, [[precision-and-recall

Pre-register primary and guardrail metrics before launch. Offline evaluation screens; online proves value.

Rapid fire — Online

Implicit feedback is noisy but cheap. Edits = strong dissatisfaction signal. A/B for causality with guardrails. Monitor latency, cost, safety—not just quality thumbs.

#How would you evaluate X? (answer template)

Use this one-page skeleton in system-design and ML rounds:

  1. Objective & surface — chat, RAG over KB, agent with tools, code assistant; failure cost (money, safety, brand).
  2. Success definition — task success rate, user resolution, cite-or-abstain policy, max latency/cost.
  3. Offline stack — regression CI → versioned golden set (sourced how, stratified how) → benchmarks only for screening.
  4. Metrics per modality — reference metrics if gold exists; execution for code; retrieval + faithfulness for RAG; tool validity for agents.
  5. Human / judge layer — when humans enter, rubric, pairwise vs pointwise, bias controls, κ on anchor set.
  6. Statistics — report p^\hat{p}p^​ with CI; paired tests for model comparisons; nnn needed for target MDE.
  7. Online — primary KPI, guardrails, experiment duration, rollback triggers.
  8. Ops — log prompts/retrieval IDs, refresh eval monthly, contamination hygiene.
Memory hook

I-O-M-G-H-S-O: Intent, Offline stack, Metrics, Judges, Humans, Statistics, Online.
